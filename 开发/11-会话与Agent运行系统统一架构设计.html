01. 统一结论

用户只理解 Session

普通聊天、事件执行和子 Agent 都表现为会话。Agent 回复“分支”直接创建新 Session，不引入 Thread 内 Branch DAG。

执行只相信 Run

排队、阶段、取消、重试、审批、用量、终态、事件序列和恢复都归 Run；Socket 和 Session 列表只是投影。

模式只改变 Policy

Direct、Plan-first、Goal 共用 LoopEngine。权限审批仍由 Read Only、Ask Risky、Auto Approve 独立控制。

总架构：Chat、Event Occurrence、Goal Wakeup 和一级子 Agent 都先创建或定位 Session， 再创建 Run，进入 RunCoordinator → LoopEngine → LoopPolicy。

03. 第一性原则

  1. 容器与执行分离：Session 保存可阅读历史；Run 保存一次执行生命周期。Session 不能承担 running/failed 的唯一真相。
  2. 模型提出，状态机裁决：模型可以请求工具、委托、提交结果或询问用户，但不能直接修改系统终态。
  3. 数据库先于广播：状态和事件先落 SQLite，再推送 Socket；重连按 seq 重放。
  4. 一个控制动作一个语义：普通工具可批量；委托、提交结果、询问用户必须独占决策，不能靠优先级静默跳过其他调用。
  5. 完成必须可验证：Direct 的最终回答、Plan 步骤、Goal 条件和子任务结果分别由 Policy 验证。
  6. 权限不因模式扩大：执行模式、事件触发和子 Agent 都不能绕过 Approval Mode 与工作区限制。
  7. 所有循环有边界：每个 Run 有 turn、token、工具、时间上限；Goal 续跑创建新 Run，不使用无限 while。
  8. 领域自治不等于系统隔离：角色系统拥有角色与视觉资源，执行系统拥有 Run；二者通过不可变版本引用和领域事件协作，不能互相复制状态，也不能只靠 UI 临时拼接。

04A. 角色系统不是附属 UI：全局集成模型

08 可以保持独立的领域边界，但角色是聊天、事件和子 Agent 的执行主体，不能只在渲染时读取一个 character_id。统一架构采用“角色拥有定义与资源，Session 建立关系，Run 固化执行快照， RunEvent 输出语义，CharacterRuntime 负责表现”的闭环。

Plan / Goal跨 Run 续跑默认仍由同一角色承担；若用户明确换角色，应创建新的执行绑定并留下审计事件。Goal owner character 与每个 Run 的 revision
桌面角色窗口订阅 CharacterPresence，而不是直接监听某一个 Socket。多个会话同时运行时，由前台会话、用户关注和状态优先级仲裁展示。窗口绑定的 character_id、surface 与 focus session

资源生命周期与引用安全

  • 角色资源不塞入 runs/sessions：图片、视频、Sprite Sheet 和 manifest 仍由 CharacterAssetStore 管理；Session/Run 保存的是稳定 revision 引用和快照哈希，不复制二进制资源。
  • Revision 发布后不可变：编辑角色生成新 revision。当前 Run 永不漂移；跟随最新版本的 Session 在下一次 Run 创建时解析新 revision。
  • 删除采用归档与延迟回收：角色或 revision 被历史 Run、事件 Occurrence、固定 Session、导出任务引用时只能 archived；资源在引用归零、保留期结束且无活动播放器后才可 GC。
  • 视觉缺失不阻断执行：CharacterRuntime 按动画 → 立绘 → 名称降级；人格或执行配置缺失则 Run 创建失败并给出结构化错误，二者不能混为一类。
  • 动作是投影，不是执行真相：刷新、断线和桌面窗口重开后，从持久化 RunEvent 重建 Presence；随机眨眼等本地自动行为无需写入 RunEvent。
边界结论：不把动画文件生命周期塞进 Run/Session 表，并不意味着 08 与执行系统隔离。 Run/Session 必须保存足以解析角色和复现执行的稳定引用；角色系统必须消费统一运行事件，并对历史引用负责。

05. 会话、消息编辑与分支

操作用户语义持久化语义
用户消息复制复制原文。不修改状态。
用户消息编辑从修改后的意图重新执行当前会话。创建 MessageRevision；后续 Turn 标记 superseded，不物理删除；创建新 Run。
Agent 消息复制复制最终可见回答。不修改状态。
Agent 消息分支从这里开始另一个会话。创建新 Session，复制截止该消息的有效上下文，保存 fork 来源。

会话名由服务端原子生成：原会话名-分支1、原会话名-分支2。分支 Session 与子 Agent Session 是不同关系： 前者使用 forked_from_session_id，后者使用 parent_session_id。

消息继续支持 token/s：流式阶段显示估算值，Run 完成后以服务端统计覆盖，并归属具体 Assistant message 和 Run。

07. 模型决策与控制动作

type AgentDecision =
  | { type: 'respond'; content: string }
  | { type: 'call_tools'; calls: ToolCall[] }
  | { type: 'delegate_to_agent'; request: DelegateRequest }
  | { type: 'submit_result'; result: ResultSubmission }
  | { type: 'ask_user'; request: QuestionRequest }

delegate_task 和 task_complete 的旧特殊工具实现直接删除。新的 delegate_to_agent、submit_result、ask_user 属于 ControlRegistry， 不进入普通 ToolRegistry。

决策服务端裁决结果
call_tools绑定、权限、工作区、并发组、超时与幂等检查。执行工具并进入下一轮。
delegate_to_agent调用者必须是顶层 Session；Group、角色能力和权限不得升级。原子创建 AgentTask + 一级子 Session + 子 Run。
submit_resultCompletionEvaluator 检查 Plan/Goal/子任务/验证要求。接受后完成；拒绝时返回未满足条件并继续。
ask_user保存问题和 Checkpoint。Run 进入 awaiting_input，释放运行资源。
respondDirect 可完成；Plan/Goal 由 Policy 判断是否只是中间说明。完成或继续。
控制动作必须独占一轮。控制动作与普通工具混用、或多个控制动作同时出现时，整批不执行并返回协议错误； 禁止“某个控制工具优先，其余调用静默跳过”。

08. Run 状态、阶段与可靠性

queued → preparing → running
                       ├─ awaiting_approval → queued
                       ├─ awaiting_input    → queued
                       ├─ paused            → queued
                       └─ completed | failed | cancelled
                          max_turns | budget_exhausted | interrupted

Run 的 status 表示生命周期；phase 表示当前正在做什么：

context历史与压缩
→
model请求与流式
→
tools工具批次
→
delegate子任务
→
verify完成验证
→
finalize结果与清理
  • 每个 Run 只有一个终态事件，使用条件更新保证 exactly-once。
  • 取消先进入 cancelling；旧 Run 的 Promise、工具和资源真正退出前，不释放同 Session 互斥。
  • 模型请求的瞬时重试使用独立 attempt 缓冲，不能拼接上一 attempt 的 delta/tool calls。
  • MCP 和临时资源统一由 RunResourceScope 在 finally 中关闭。
  • 意外异常由 Run boundary 统一记录 failed，Runner 不得吞掉错误。
  • RunEvent 使用单调 seq；数据库提交后再广播，客户端通过 after_seq 重放。

10. 一级子 Agent

唯一允许的结构：
母 Session
├─ 子 Session 1
└─ 子 Session 2
  1. 只有 parent_session_id = null 的顶层 Session 能收到 delegate_to_agent 控制能力。
  2. 有 active_group 时，只能调用组内且角色为 sub/both 的 Agent；无 Group 时只能调用自己。
  3. 子 Session 的 ControlRegistry 不包含 delegate；服务端创建接口也拒绝以子 Session 为父。
  4. 每次委托创建一个 AgentTask、一个子 Session 和一个子 Run；不提供 instances 参数。
  5. 子 Agent 调用完整 LoopEngine，而不是只执行一次 innerLoop。
  6. 子权限不得高于母会话；Provider、模型、工作区、active_group 和 Approval Mode 使用明确快照。
  7. 前台模式由母 Run 等待；后台模式完成后写收件箱事件，在母 Run 安全边界注入结果。

11. 事件：定义与一次执行分离

EventDefinitiononce / cron
长期规则
→
Occurrence某一次触发
→
Event Session顶层可见会话
→
Run统一执行
  • Cron 使用真实解析器和 timezone 计算 next_fire_at；不复制 Event 并立即再执行。
  • 同一 definition + scheduled_for 唯一，调度抢占使用事务条件更新。
  • 手动运行创建 manual Occurrence，不允许前端直接 PATCH running。
  • 每个 Occurrence 只创建一个顶层事件 Session；失败重试在同 Session 创建新 Run。
  • Occurrence 结果直接来自 Run 结构化结果，不扫描消息猜测。
  • assigned_group 写入 Session.active_group；事件母 Agent 可创建一级子 Session。
  • Approval Mode 在定义中明确保存；Ask Risky 进入持久 awaiting_approval，不使用 Fake Socket。
  • 默认 overlap_policy=skip；可选 queue，首版不开放 parallel。

12. 上下文、压缩与 Checkpoint

组件职责
ContextBuilder根据有效 Turn、附件、记忆、压缩版本和动态提醒构造请求视图，不修改持久消息原文。
CompactionService裁剪旧工具结果、生成摘要、保存 summary version 与 message cursor；摘要和 cutoff 原子更新。
CheckpointService在 awaiting、暂停、预算边界和可恢复中断时保存上下文版本、Policy 状态、用量和等待项。
ModelExecutor请求级 retry、attempt 隔离、usage 和 delta；首个 attempt 残片不能污染成功结果。
ToolCoordinator普通工具校验、审批、并发组、超时、幂等和结构化结果。

孤儿 tool call 不再只在内存静默注入 [reconstructed]。ContextBuilder 可以临时修复请求， 但必须记录 integrity event，并由数据修复任务处理根因。

13. 前端统一信息架构

左侧 Session

项目下显示普通会话；事件会话单独分区。母会话下最多显示一级子会话。分支是独立顶层会话，并显示来源标识。

消息主区

用户消息：复制、编辑。Agent 消息：复制、分支。Assistant 顶部显示最终 token/s；工具与控制卡片按 RunEvent 投影。

右侧运行面板

角色、协作组、可调用成员、Approval Mode、Execution Mode、当前 Run phase、Plan 步骤、Goal、子 Agent 和事件来源。

事件中心

管理 EventDefinition；展开查看 Occurrence 历史、下一次时间、重试、结果和打开会话。

协作组选择器候选项取母角色所属 Group。无组显示“仅可调用自己”；只有一个 Group 时新会话可默认选中， 多个 Group 必须由用户选择。前端 Store 只根据 durable event 更新 Run 状态，刷新后按 seq 恢复。

17. 推荐开发顺序

P0

修复正确性

P1

P2

P3

18. 关键验收标准

  • 流式输出一半后失败重试，最终文本和工具参数不重复。
  • Abort 后立即发送新消息，同 Session 永远不会出现两个并行 Run。
  • 任意异常路径都有且只有一个 terminal RunEvent，资源全部关闭。
  • 刷新或断线后能从 after_seq 恢复消息、工具、阶段、Plan 和审批。
  • 用户编辑消息保留旧 revision；Agent 分支产生独立新 Session 和正确命名。
  • 子 Agent 能完成多轮工具 Loop，但无法获得或伪造 delegate_to_agent，数据库不存在孙会话。
  • 控制动作与普通工具混用时整批拒绝，不产生部分副作用。
  • submit_result 未满足 Plan/Goal 条件时被拒绝，并返回可执行的未满足项。
  • Cron 在正确时区和时间触发；同一 scheduled_for 只产生一个 Occurrence。
  • 事件手动运行、自动触发、失败重试各自只创建一个 Session；结果摘要来自 Run 结果。
  • Ask Risky 在事件或断线场景中可持久等待并恢复，不依赖当前 Socket。
  • Run 中途发布新角色 revision 不改变当前执行；下一次 follow_latest Run 使用新版本，pinned Session 保持旧版本。
  • RunEvent 能稳定投影 thinking、working、speaking、success、error；无动画或无立绘时分别降级且不影响执行。
  • 被历史 Run、Occurrence 或固定 Session 引用的角色 revision 无法物理删除；归档后历史会话仍可解析或明确降级。
  • 事件重试使用首次 Occurrence 已解析的角色 revision；子 Agent Session 使用目标角色自己的 revision。

19. 本轮明确不做

  • 不在 Run/Session 表中复制角色动画二进制或维护第二套资源状态；它们必须保存稳定角色 revision 引用，并参与角色资源的引用保护。
  • 不实现 Thread 内多 Branch DAG；分支就是新 Session。
  • 不允许递归子 Agent、孙会话或 child AgentTask。
  • 不为旧数据库、旧控制工具、旧策略名和旧事件 API 写兼容层。
  • 不让 EventExecutor、子 Agent 或 Goal 各自复制一套 Loop。
  • 不允许模型直接宣告系统完成，也不允许客户端任意 PATCH 领域状态。
  • 不在 Run 基础设施稳定前实现 Plan-first/Goal 的模式切换。
最终实施判断：先修 Run 正确性，再统一所有入口，然后增加 Plan/Goal。 这能让消息交互、一级子 Agent、事件和执行模式共用同一套可靠基础，而不是继续在现有函数上叠加特殊分支。
