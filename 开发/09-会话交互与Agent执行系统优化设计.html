Architecture Decision Document

会话不是一串消息，
而是一棵可恢复的执行树

本设计用于升级天枢“实际干活”的会话体验与 Agent Loop：支持消息复制、编辑后分支、回退与恢复， 支持可观察、可暂停、可唤醒的子 Agent，并将 Plan 与 Goal 从提示词选项升级为可持久化、可验证的系统能力。

参考 LeAgent参考 OpenCode 对齐 Codex Goal / Subagent 语义面向桌面 Agent

01. 设计结论

核心决策：把 Thread / Branch / Turn / Run / Goal / Plan / AgentTask 拆成不同的一等对象。消息负责“说了什么”，Run 负责“执行了什么”，Goal 负责“长期要做到什么”。

历史不可破坏

编辑消息不再删除后续历史，而是从目标 Turn 新建分支。回退只移动分支指针，允许撤销回退。

执行可以恢复

WebSocket 断开不等于任务消失。Run、Checkpoint 和事件序列进入数据库，重启后也能恢复或明确终止。

目标可以续跑

Goal 有完成条件、预算、状态和验证证据。自动续跑有边界，不把“无限循环”伪装成智能。

天枢当前的 Plan / Ask / Bypass 更接近“工具审批策略”，不应继续占用“Plan”这个名称。 建议把它重命名为 Review Mode（审批模式），再独立增加 Execution Mode：Direct / Plan / Goal。

02. 天枢现状与主要缺口

已有能力当前实现主要缺口
消息历史按 session 顺序保存 user / assistant / tool 消息没有 Turn、Branch、Run 归属，无法稳定表达分支历史
编辑/重置resetToMessage 与 keepFirst 删除目标之后消息破坏历史，无法比较旧回答，也不能撤销
执行调度每个 session 一个内存 runner，FIFO 排队，CancelScope 中止进程重启即丢；Socket 事件无法补放；缺少 durable checkpoint
子 Agent创建带 parent_id 的子会话并执行，返回摘要缺少持久任务对象、后台运行、follow-up、pause/resume/wake
规划有审批策略与文档层面的 loop/checkpoint 设想没有版本化 Plan 与 Step 状态，也没有证据绑定
长期目标暂无独立 Goal 实体无法跨 Turn 续跑、计量预算、判断真正完成
前端消息基础气泡、工具状态、推理内容；更新时自动滚底缺复制/编辑/重试/分支；长会话虚拟化与智能滚动不足
现有 02-Loop设计.md 中关于压缩、恢复、Steer、Checkpoint 的方向是正确的； 本文把这些意图补成可实施的数据边界、生命周期和 UI 交互，而不是推倒重写全部 Loop。

04. 核心对象分层

Thread用户看到的会话容器
→
Branch历史树中的一条路径
→
Turn一次用户意图与响应
→
Run一次实际执行尝试
→
Event / Part流、工具、文本与状态

对话结构

  • Thread：标题、角色、项目、默认模型等外壳。
  • Branch：指向一个 head Turn；同一 Thread 可有多条。
  • Turn：以用户输入为边界，可有多个 Run（重试/重新生成）。
  • Message Part：文本、推理摘要、工具调用、附件、引用。

工作结构

  • Run：一次有状态的 Agent Loop，必须有终态。
  • Goal：跨多个 Turn/Run 的长期目标与完成标准。
  • Plan：Goal 或 Run 下版本化的步骤、依赖和证据。
  • AgentTask：可独立等待、继续、取消的子执行单元。
关键关系：一个 Turn 可以因“重新生成”产生多个 Run；一个 Goal 可以驱动多个 Turn； 一个 Run 可以创建多个 AgentTask；一个 AgentTask 可关联独立子 Thread，但不能只靠子 Thread 表达生命周期。

05. 消息交互设计

5.1 消息操作栏

对象操作规则
用户消息复制、编辑并分支、再次发送、引用、固定编辑默认保留原路径；有附件时一并复制元数据
助手消息复制 Markdown、复制纯文本、重新生成、反馈、查看 Run重新生成在同一 Turn 下创建新 Run，不伪造新的用户消息
代码块复制、应用、保存、打开文件“应用”仍走权限审批和工作区冲突检测
工具结果展开、复制摘要、复制原始输出、定位来源默认折叠超长输出，保留完整 artifact 引用
整轮复制本轮、Fork、从此处继续、导出内部推理不进入复制内容；只复制可展示推理摘要

5.2 长会话体验

  • 用户向上滚动后锁定当前位置，不因流式增量强制滚到底部；显示“有新内容”按钮。
  • 历史分页加载；超过阈值后虚拟化渲染，工具输出与附件按需加载。
  • 运行中消息保持固定锚点，完成后再计算最终高度，避免界面跳动。
  • 支持按 Turn、工具、文件、角色、Run 状态搜索，而不是只做全文匹配。

06. 编辑、分支、回退与恢复

6.1 编辑消息的默认语义

  1. 选择历史用户消息，进入编辑态。
  2. 提交后创建新的用户 Message/Turn，其 parent_turn_id 指向被编辑点之前的 Turn。
  3. 创建新 Branch，并把它设为当前 Branch；原 Branch 完整保留。
  4. 在新 Turn 上创建 Run。UI 提供 1 / 2 分支切换器。
禁止继续使用“删除后续消息 + 改写原消息”作为编辑实现。它会破坏审计、Plan 证据、工具调用来源与 Goal 用量统计。

6.2 四种容易混淆的操作

操作产生什么适用场景
重新生成同一 Turn 的新 Run提示不变，只想换一个答案/执行尝试
编辑并分支新 Turn + 新 Branch + 新 Run修改历史输入并保留旧路线
Fork 会话新 Thread，复制到指定 Turn 的可见历史想把探索路线拆成独立会话
回退/恢复移动 Branch head 指针临时隐藏后续路径；支持 unrevert

对仍在运行的 Turn 不允许直接 Fork 到“半个工具调用”。用户可先中止，系统写入 interrupted 标记和 checkpoint，再从该稳定点 Fork。

07. 推荐 Agent Loop

1. 接收意图Turn / Goal / Steer
→
2. 创建 Run排队与租约
→
3. 构建上下文Branch + Memory
→
4. 推理执行Model / Tool / Agent
→
5. 检查终态完成 / 暂停 / 续跑
while run.status == "running":
  refresh_steering_inputs()
  ensure_budget_and_permission()
  compact_context_if_needed()
  response = model.stream(context)
  persist_stream_events(response)

  if response.requests_tools:
    results = execute_tools_with_policy(response.tool_calls)
    persist_parts_and_artifacts(results)
    checkpoint("after_tool_batch")
    continue

  verdict = evaluate_completion(run, goal, plan)
  transition_to(verdict)  // completed | awaiting_input | paused | continue

7.1 必须坚持的 Loop 规则

  • 数据库状态先于 Socket 展示状态；Socket 是投影，不是事实来源。
  • 每批工具执行后、等待用户前、预算耗尽前写入 checkpoint。
  • Steer 输入进入当前 Run 的安全边界：模型流结束或工具批次结束后注入，不修改已发送的模型请求。
  • 所有循环都有单 Run 上限：turn、token、工具次数、墙钟时间；Goal 续跑通过新 Run 实现。
  • 完成必须由“回答结束”和“目标验证”共同判断，不能只看模型是否输出文本。

08. Run、事件重放与恢复

Run

记录 mode、model、branch、goal、plan、parent run、开始/结束、用量和终止原因。

Checkpoint

记录上下文快照引用、工具状态、待审批项、计划版本与恢复游标。

Run Event

单调递增序号的 append-only 事件，用于断线补放、审计与 UI 重建。

8.1 Run 状态机

queued → running → paused / awaiting_input / completed / failed / cancelled / interrupted

  • paused：主动暂停，可从 checkpoint 恢复。
  • awaiting_input：需要用户选择、审批或补充信息。
  • interrupted：进程异常、租约过期或强制关闭；恢复前需健康检查。
  • completed：Run 本身完成，不代表 Goal 必然完成。

桌面端重连时携带每个 Run 的最后事件序号 after_seq；服务端先补放缺失事件，再进入实时订阅。 这会替代当前“只依赖 persistent listeners”的脆弱恢复方式。

09. Plan 模式不是审批模式

建议把当前 strategy: plan / ask / bypass 迁移为 review_mode: always / risky / bypass；新增 execution_mode: direct / plan / goal。

9.1 Plan 的结构

{
  "goal": "完成桌面端登录页重构",
  "version": 3,
  "status": "active",
  "steps": [{
    "id": "step_2",
    "title": "修改表单校验",
    "depends_on": ["step_1"],
    "status": "in_progress",
    "verification": ["pnpm test login"],
    "evidence_artifact_ids": []
  }]
}
  • Plan 是版本化 artifact，不是每次渲染重新解析 Markdown。
  • Step 状态包括 pending / in_progress / blocked / completed / skipped / failed。
  • 修改计划产生新版本；旧 Run 固定引用当时版本，保证可追溯。
  • Todo 是 Plan 的轻量视图；不能用一个前端 Todo 数组替代计划实体。
  • Plan 模式可配置“先只读规划，用户批准后执行”；审批仍由 Review Mode 决定。

10. Goal 模式：有边界的长期执行

10.1 Goal 定义

Outcome

最终要交付的可描述结果，而不是“继续优化”这类无终点动词。

Constraints

目录、权限、不可触碰内容、质量门槛、时间或资源限制。

Verification

测试、构建、人工检查、文件或外部状态，决定是否真正完成。

Budget

Token、时间、Run 次数、工具次数与并发上限；用量跨 Run 累计。

10.2 Goal 状态

active paused awaiting_input verifying completed blocked cancelled

10.3 自动续跑策略

  1. 当前 Run 结束后，Goal Evaluator 检查完成证据、剩余计划、阻塞项和预算。
  2. 若可继续，创建新的 Goal Run；不要在一个无限 while 中堆积上下文。
  3. 若需要用户决定，转为 awaiting_input 并生成明确问题。
  4. 若外部条件未满足，登记 Wake Condition；条件满足时调度新 Run。
  5. 验证通过才标记 completed；模型自称“完成”只是一条候选证据。
Goal 不扩大权限。原会话不能写的目录、不能执行的命令、需要审批的操作，在自动续跑和子 Agent 中仍然受限。

10.4 用户操作

创建、暂停、恢复、编辑、清除、查看用量与完成证据。编辑 Goal 产生 revision；修改目标本身时重新评估 Plan，但保留历史用量与审计。

11. 子 Agent：从一次性函数升级为可管理任务

11.1 AgentTask 生命周期

created → queued → running → paused / awaiting_input / completed / failed / cancelled

动作含义天枢建议接口
Spawn创建新任务，可前台等待或后台执行POST /agent-tasks
Follow-up / Steer向已有任务追加信息，不新建一个“陌生”子 AgentPOST /agent-tasks/:id/inputs
Wait父 Run 等待一个或多个任务状态变化POST /agent-tasks/wait
Interrupt安全中断并写 checkpointPOST /agent-tasks/:id/interrupt
Resume / Wake从 checkpoint 恢复，或被事件条件唤醒POST /agent-tasks/:id/resume
Close / Archive释放活跃资源，历史仍可查看POST /agent-tasks/:id/archive

11.2 唤醒条件

  • 用户或父 Agent 发来 follow-up；
  • 依赖任务完成、失败或提交中间结果；
  • 到达指定时间或重试退避时间；
  • 文件、构建、外部服务等受控事件发生；
  • 父 Goal 进入需要该角色继续工作的 Plan Step。

11.3 完成结果如何回到父会话

  • 父 Run 正在运行：在下一个安全边界注入 agent_task.completed steer。
  • 父 Run 空闲：创建收件箱通知与可展开结果卡片，不擅自生成一条“用户消息”。
  • 父 Goal 活跃：Goal Coordinator 可据结果创建下一 Run。
  • 任务失败：附带失败类型、已完成工作、checkpoint 和可重试建议，不只返回字符串异常。
保留现有“子会话隔离上下文”的做法，但新增 AgentTask 作为生命周期真源。子会话是可视化与上下文容器，AgentTask 才是可唤醒的工作单元。

12. 前端信息架构

会话顶部

当前 Branch、Execution Mode、Review Mode、模型/角色、运行状态、Goal 用量。

消息主区

Turn 卡片、消息操作栏、分支切换、Run 尝试切换、工具与证据。

工作侧栏

Plan Steps、Goal 状态、活跃/已完成子 Agent、审批与通知收件箱。

12.2 状态呈现规则

  • “正在思考”只表示模型流；“正在工作”表示 Run；“目标进行中”表示 Goal，三者不可混用。
  • 后台子 Agent 以任务卡展示角色、任务摘要、阶段、耗时、最后事件和控制按钮。
  • 计划、目标、审批默认在侧栏；消息中只插入重要快照，避免系统卡片淹没对话。
  • 角色动画可映射工作状态：idle / thinking / tool / waiting / success / error，但状态源必须来自 Run/Task，而非前端计时器猜测。

13.1 ID 与删除策略

  • 服务端生成稳定字符串 ID（ULID/UUIDv7），前后端统一类型；不混用客户端临时字符串与数据库自增数字。
  • 历史对象采用 append-only + superseded / archived 标记；仅缓存与过期事件允许物理清理。
  • 大工具输出、截图、补丁等进入 Artifact Store，消息只保存摘要、MIME、哈希与引用。

15. 从当前系统兼容迁移

  1. 为每个现有 session 创建默认 Branch；按 user 消息边界推导 Turn。
  2. 为已有 assistant/tool 连续段创建历史 Run，状态标为 completed 或 unknown-completed。
  3. 新增字段全部可空，旧 API 继续工作；新前端按 capability flag 开启。
  4. 把 resetToMessage 改造成“移动 Branch head”，保留旧路由但停止物理删除。
  5. 当前 sub_agent.started 同步创建 AgentTask；后续再将执行权迁入 durable coordinator。
  6. 将 strategy 字段映射为 Review Mode；新增 Execution Mode，不直接篡改旧用户偏好。
第一阶段不要求把全部旧消息拆成精细 Part。可以先保持 messages.content/tool_*， 只补 Turn、Branch、Run 外键；结构化 Part 在后续迁移。

16. 权限、并发与工作区冲突

  • 子 Agent 继承父任务权限上限，只允许缩小，不允许自行提升。
  • Goal 自动续跑沿用创建时权限快照；高风险动作每次仍可要求审批。
  • 每个 Thread 同时只允许一个“写主线”的 Run；只读分析和独立工作树任务可并行。
  • 并行写任务优先分配 worktree / 独立目录；合并回主工作区前生成冲突预检。
  • Run 使用数据库租约与 heartbeat，租约过期转 interrupted，禁止两台 worker 同时恢复同一 Run。
  • 限制子 Agent 深度、并发数、总预算与单任务预算；超限时进入可解释的 paused，而非静默失败。
  • 复制与导出默认过滤密钥、隐藏字段和内部推理；工具原始输出按权限展示。

17. 推荐开发分期

P0

统一语义与基础迁移

确定 Thread/Turn/Branch/Run 命名；新增表与 capability flag；Plan 审批策略改名。约 1 周。

P1

消息体验与分支

复制、编辑并分支、重新生成、Fork、revert/unrevert、分支切换；智能滚动与历史分页。约 2–3 周。

P2

Durable Run 与事件重放

Run/RunEvent/Checkpoint、租约、断线补放、重启恢复；替换纯内存 runner 真源。约 3–4 周。

P3

Plan Artifact

计划版本、步骤依赖/状态/证据、批准后执行、侧栏与消息快照。约 2 周。

P4

可唤醒子 Agent

AgentTask、后台任务、follow-up、wait/interrupt/resume、完成自动通知和结果注入。约 3–4 周。

P5

Goal Mode

Goal/预算/验证/续跑协调器、Wake Condition、暂停恢复和完成证据。约 3 周。

P6

并行工作与可观测性

worktree 隔离、冲突检测、运行时间线、成本分析、失败归因和压力测试。持续演进。

工期为单一小团队的粗略估计；P1 可独立先交付用户价值，P2 是 P4/P5 的稳定性前提。

18. 验收标准

消息与历史

  • 编辑任意历史用户消息后，旧路径仍可一键切回。
  • 重新生成不复制用户消息，并能比较多个 Run。
  • 回退后可以恢复；数据库不存在意外 DELETE。
  • 万条消息下滚动、搜索与流式输出仍可用。

Run 与恢复

  • 刷新和 Socket 断开后能补回所有缺失事件。
  • 服务进程在工具批次后崩溃，可从 checkpoint 恢复。
  • 每个 Run 都有明确终态、终止原因和用量。
  • 同一 Run 不会被两个 worker 同时执行。

Plan / Goal

  • 计划修改保留版本，步骤完成有证据来源。
  • Goal 能暂停、恢复、编辑并显示预算消耗。
  • 没有验证证据时，系统不会仅凭模型声明完成。
  • 预算耗尽或需要决策时安全暂停。

子 Agent

  • 已有任务能 follow-up，不必重开子会话。
  • 后台完成后无需父 Agent 轮询即可收到事件。
  • 中断后可恢复，失败能展示 checkpoint 与原因。
  • 权限、深度、并发和预算限制可验证。

最终判断

优先顺序应是：先保住历史，再保住执行，最后让系统自动续跑。 也就是 Branch → Durable Run → AgentTask → Goal。若跳过前两层直接做 Goal，得到的只会是不可恢复、不可审计的长循环。
