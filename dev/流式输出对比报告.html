一、总体架构

A = deepseek-harness（保守派：流式期纯文本、定稿一次付清）；B = opencode-dev（激进派：边流边高亮、节流削峰）。

A · deepseek-harness
  • 栈：React + memo/useMemo 缓存元素树
  • 引擎：自研 mdast 管线 —— parse.ts（GFM+数学）→ incremental.ts（增量切分）→ render.tsx（语义 React 元素）
  • 数据源：BlockAssembler 把 StreamChunk 组装为 text / reasoning / tool-call / image 块
  • 入口：<MarkdownText streaming> 单 prop 切换流式 / 定稿两条管线
  • 哲学：流式零闪烁零跳动，复杂度保证严格（每块只 parse O(1) 次）
B · opencode-dev
  • 栈：SolidJS 细粒度响应 + 手动 DOM 操作
  • 引擎：marked lexer 投影 → 异步产 HTML → morphdom 打补丁；双层缓存免重绘
  • 数据源：part 存储，readPartText 读累积增量
  • 入口：PacedMarkdown（流式）/ Markdown streaming=false（定稿）
  • 哲学：即时反馈优先 —— 未闭合代码块立即流式高亮，remend heal 尾部语法
一句话总结：A 把功夫花在「解析层」（冻结 + 增量 + 稳定 key），B 把功夫花在「感知层」（节流打字机 + Worker 流式高亮 + morphdom 微更新）。两者不互斥——天枢完全可以取长补短。

二、核心机制逐项对比

六个维度：增量解析 / 未闭合语法处理 / 输出节奏 / 代码块高亮 / 视觉指示 / DOM 更新与安全。

1. 增量解析与免重绘策略 两家共识：别整段重绘

A · 冻结式增量解析（130 行）

  • 冻结除最后 2 个 top-level block 外的全部块（UNSTABLE_TAIL_BLOCKS = 2），每 chunk 只重解析尾部
  • 冻结块 key = 源码绝对偏移量，跨 chunk 稳定 → React reconcile 而非 remount，选中态/滚动不丢
  • text.startsWith(prev) memcmp 判定追加/重置；重置时 bump generation 全量丢弃缓存
  • render() 幂等：text 未变直接返回缓存结果数组

B · 全量 lex + 双层缓存

  • 每次 marked.lexer(text) 全量 lex，最后一个非空 token 视为 live 区
  • markdown-cache 按 key:index:mode 缓存 {raw, hash, html}，raw 未变直接复用（LRU touch）
  • canReusePendingBlock：mode 相同且 code 前缀延伸时复用已渲染块
  • 围栏快路径：closesFence(tail.raw, suffix) 发现后缀不含 ``` 时，suffix 直接拼进现有 code block，完全跳过 re-lex
A 的复杂度保证更严格（每块源区只 parse O(1) 次）；B 用全量 lex + 缓存命中换实现简单性，长回复下 lex 本身仍是 O(n)，但有快路径和节流兜底。

2. 流式中「未闭合语法」的处理哲学 A 保守 B 激进

场景A · deepseek-harnessB · opencode-dev
未闭合代码围栏流式期间渲染纯文本，turn 结束 finalize 时一次性换成高亮 CodeBlock当作 live code block 立即流式高亮
引用式链接 / 脚注已知偏差：定义落在冻结边界另一侧时字面渲染，定稿全量解析 self-heal（注释中明确文档化）remend 库主动 heal 尾部（linkMode: text-only），流式期尽量正常显示

A 选择「保守 + 定稿修正」，换来流式期零闪烁、零布局跳动；B 选择「激进即时」，视觉反馈更快但依赖 remend 的 heal 质量。

3. 输出节奏控制（打字机效果）B 独有 · 性价比之王

A

没有节奏层，chunk 到达即渲染，依赖增量解析保证单次成本低。

B · PacedMarkdown / createPacedValue

// message-part.tsx 252–344 行
TEXT_RENDER_PACE_MS   = 24     // 每 24ms 一拍 ≈42fps
TEXT_RENDER_IMMEDIATE = 512    // 落后≤512字符直通
step(size)                     // 步长自适应:
                               // ≤12→2字, ≤48→4字,
                               // ≤96→8字, 否则 size/4 上限256
TEXT_RENDER_SNAP               // 追加终点吸附空白/标点,
                               // 避免单词被劈开
积压小（≤512 字符）零延迟直出；积压大时匀速放出削平渲染尖峰。这层与渲染引擎完全解耦，约 40 行代码，是对「感知流畅度」性价比最高的组件。

4. 代码块流式高亮 B 独有 · 工程量大头

A

finalize 时一次性挂载 CodeBlock（highlight.ts），流式期间只有纯文本。流式期零高亮开销，实现成本低一个数量级。

B · Shiki Worker 全家桶

  • Web Worker 内跑 ShikiStreamTokenizer（@shikijs/stream），主线程零阻塞
  • token 分 stable / unstable 两段输出；队列带 supersede（新请求作废旧请求）、dispose、unavailable 三级降级
  • DOM 侧 updateCodeBlock 做 span 级增量更新：算公共前缀 keep 数，只删/追尾差 spans
  • 完成后用整段 codeToTokens 重置一次保证终态精确
  • 附带 copy 按钮（morphdom 保护）、shell 语言识别、inline code 自动链接化

6. DOM 更新方式 与 安全降级 路线迥异

A · 全交 React diff

优化点是 frozen elements 缓存 + 稳定 key，让 diff 面积只剩 tail。

安全

  • 管线内建：禁 raw HTML、相对链接、unsafe 协议；仅放行绝对 HTTP(S) 图片
  • fileMentions 仅在定稿渲染启用——避免流式词汇未定型时烘焙过期 handler（细节值得学习）

B · 三层手段并用

  • block 级：data-markdown-key/hash 相同 → 直接 return 零操作
  • 普通块变化：morphdom 最小补丁，回调保护 copy-button、跳过 isEqualNode 节点
  • code block：绕过 morphdom，自己的 span 增量算法

降级

sanitizeMarkdown 清洗；fallback 为转义 + <br>；SSR 分支、worker 不可用降级、initialValue 同步首帧全覆盖。

四、给天枢的借鉴清单（按性价比排序）

前两项加起来不到一天工作量，感知提升立竿见影；后面按需投入。

  1. 节奏层 —— 24ms 一拍 + ≤512 字符直通 + 步长自适应 + 标点吸附。← 抄 B
    约 40 行、与渲染引擎无关，「样式优化」最直接的抓手。
  2. turn-status shimmer —— 状态行文字渐变 + prefers-reduced-motion 降级。← 抄 A
    纯 CSS 几行搞定「正在生成」氛围感。
  3. 未闭合 fence 快速通道 —— 检测到尾部是不完整代码块时，新字符直接追加进 pre/code，跳过整段重渲染。← 抄 B 思路
    这是流式卡顿的最大单点来源。
  4. 代码块流式高亮 —— Shiki stream + Worker + stable/unstable 增量 span。← 抄 B · 工程量大
    仅当天枢代码块占比高再投入；否则退用 A 方案（流式纯文本、定稿高亮），成本低一个数量级。
  5. 块级缓存 + 稳定 key —— 冻结块复用渲染结果，key 取源偏移或 key:index:mode。两家共识
    保证越写越长时前面内容零重排。
  6. remend 式尾部 heal（可选）—— 让链接/列表流式期就正常成形。← 抄 B
    接受「定稿才修正」的话可以不做。
  7. 中断标记 & reduced-motion —— abort 后的 stopped 标记和无障碍降级。← 抄 A
    完整性细节。
