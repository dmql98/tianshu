# 会话界面流式输出样式对比报告

> 对比对象：
> - **A = deepseek-harness**（`packages/client/ui-primitives/src/markdown/` + `packages/client/ui-conversation/src/client/chat/`），技术栈 React + 自研 mdast 管线
> - **B = opencode-dev**（`packages/session-ui/src/components/markdown*.ts(x)`），技术栈 SolidJS + marked + morphdom + Shiki Worker
>
> 目的：为天枢会话界面流式输出的样式优化提供选型参考。

---

## 一、总体架构对比

| 维度 | A · deepseek-harness | B · opencode-dev |
|---|---|---|
| UI 框架 | React（memo/useMemo 缓存元素树） | SolidJS（细粒度响应 + 手动 DOM 操作） |
| Markdown 引擎 | 自研 mdast 管线：`parse.ts`（GFM+数学）→ `incremental.ts`（增量切分）→ `render.tsx`（语义 React 元素） | marked lexer 投影（`markdown-stream.ts`）→ 异步产 HTML 字符串 → `morphdom` 打补丁 |
| 数据来源 | `BlockAssembler` 把 StreamChunk 组装成 text/reasoning/tool-call/image 块，UI 按 block 序列渲染 | part 存储（text/reasoning part），`readPartText` 读累积增量 |
| 流式开关 | `<MarkdownText streaming>` 单一 prop 切换流式/定稿两条管线 | `PacedMarkdown`（流式）/ `Markdown streaming=false`（定稿）两个入口 |

## 二、核心机制逐项对比

### 1. 增量解析 / 免重绘策略

**A（IncrementalMarkdownParser，130 行）**
- 冻结除**最后 2 个 top-level block** 外的所有 block（`UNSTABLE_TAIL_BLOCKS = 2`），每个 chunk 只重新解析源文本尾部；
- 冻结块的 render key = **源码绝对偏移量**，跨 chunk 稳定 → React 走 reconcile 而**不是 remount**，滚动位置/选中态不丢；
- 用 `text.startsWith(prevText)` 做 O(prefix) memcmp 判定 append/reset，非追加输入 bump `generation` 并整体丢弃缓存；
- `render()` 幂等：text 未变直接返回上次结果数组。

**B（project/stream + markdown-cache）**
- 每次 `marked.lexer(text)` **全量 lex**，但把最后一个非空 token 视作 "live"，其余为 "full"/"code"；
- 免重绘靠**两层缓存**：
  - `markdown-cache.tsx`：按 `cacheKey:index:mode` 缓存 `{raw, hash, html}`，raw 未变直接复用 HTML（LRU touch）；
  - `canReusePendingBlock`：mode 相同且 code 块 raw 前缀延伸时复用已渲染块；
- 针对**未闭合围栏**有一条快路径：`closesFence(tail.raw, suffix)` 检测到后缀不含 ``` 时，suffix 直接拼进现有 code block，**完全跳过 re-lex**。

**结论**：A 的复杂度保证更严格（每块源区只 parse O(1) 次，无全量 lex）；B 用全量 lex + 缓存命中换实现简单性，长回复下 lex 本身仍是 O(n)，但有快路径和节流兜底（见 §3）。

### 2. 流式中"未闭合语法"的处理哲学

| | A | B |
|---|---|---|
| 未闭合 fence | 流式期间渲染为**纯文本**，turn 结束 finalize 时一次性换成高亮 CodeBlock | 当作 live code block **立即流式高亮** |
| 未闭合引用式链接/脚注 | **已知偏差**：定义落在冻结边界另一侧时字面渲染，等定稿全量解析 self-heal（注释中明确文档化） | `remend` 库主动 heal 尾部（linkMode: text-only），尽量流式期就正常显示 |
| 数学公式 (KaTeX) | finalize 才渲染 | 不涉及 |

A 选择"保守 + 定稿修正"，换来流式期零闪烁、零布局跳动；B 选择"激进即时"，视觉反馈更快但依赖 remend 的 heal 质量。

### 3. 输出节奏控制（打字机效果）—— B 独有

`message-part.tsx` 里的 `PacedMarkdown` / `createPacedValue`：

```
TEXT_RENDER_PACE_MS    = 24    // 每 24ms 一拍
TEXT_RENDER_IMMEDIATE  = 512   // 落后 ≤512 字符直接同步，不打字机
step(size)             // 每拍追 2→4→8→…→256 字符，按积压量自适应
TEXT_RENDER_SNAP       // 追加终点吸附到空白/标点，避免单词被劈开
```

- 积压小（≤512 字符）时零延迟直出；积压大时以约 42fps 的节奏匀速放出，削平渲染尖峰；
- 这层与渲染解耦，是对"感知流畅度"性价比最高的一个组件。

A 没有节奏层，chunk 到达即渲染（依赖增量解析保证单次成本低）。

### 4. 代码块流式高亮 —— B 独有的深度实现

`markdown-shiki.worker.ts` + `markdown-worker*.ts` + `markdown-code-state.ts`：

- **Web Worker** 中跑 `ShikiStreamTokenizer`（@shikijs/stream），主题 OpenCode，主线程零阻塞；
- tokenizer 输出分 **stable / unstable** 两段 token；worker 队列带 supersede（新请求到来丢弃旧请求）、dispose、unavailable 三种降级路径；
- DOM 侧 `updateCodeBlock` 做真正的**增量 span 更新**：`shouldResetCodeTokens` 判定语言/generation/raw 变化是否需要重建，否则计算公共前缀 `keep` 数，只删除/追加尾差 spans；
- 代码块完成后用整段 `codeToTokens` 重置一次，保证终态精确；
- 附带 copy 按钮（morphdom 保护其不被补丁覆盖）、shell 语言识别、inline code 自动链接化。

A 的对应物是 finalize 时一次性挂载 `CodeBlock`（highlight.ts + CodeBlock.module.css），流式期间只有纯文本。

### 5. 流式期间的视觉指示

| | A | B |
|---|---|---|
| 进行中指示 | `.turnStatus` **shimmer 文字渐变动画**（1.8s linear infinite，background-clip:text），附 tabular-nums 计时器；`prefers-reduced-motion` 下完全关闭动画 | 无光标/无 shimmer；靠文字本身滚动 + copy 按钮 hover 出现 |
| 推理过程 | `ReasoningRow`："Think" 折叠摘要行，展开为缩进灰字，running 态绑定最后一个 block | reasoning part 与正文一样走 PacedMarkdown 流式 |
| 中断态 | `interrupted` prop → 追加 "stopped" 标记 | `data-interrupted` 属性 + copy 包装 |

两边都没有打字光标（caret/blink）类装饰。

### 6. DOM 更新方式

- A：全部交给 React diff；优化点是 frozen elements 缓存 + 稳定 key，让 diff 面积只剩 tail。
- B：三层手段并用 ——
  1. block 级：`data-markdown-key/hash` 相同直接 return（零操作）；
  2. 普通 block 变化：`morphdom` 最小化 HTML 补丁，且回调里保护 copy-button、跳过 isEqualNode 节点；
  3. code block：绕过 morphdom，自己的 span 增量算法（§4）。

### 7. 安全与降级

- A：管线内建安全 —— 禁 raw HTML、相对链接、unsafe 协议；仅放行绝对 HTTP(S) 图片；fileMentions 仅在定稿渲染启用（避免流式词汇未定型时烘焙过期 handler，这个细节值得学习）。
- B：`sanitizeMarkdown(marked.parse(...))`；fallback 为转义 + `<br>`；SSR 分支、worker 不可用降级、initialValue 同步首帧都处理了。

## 三、性能画像总结

| 场景 | A | B |
|---|---|---|
| 每 chunk 主线程成本 | O(尾部重解析) + frozen 引用收集，理论最优 | O(n) 全量 lex（有 fence 快路径）+ 缓存命中的 HTML 复用 |
| 高亮开销位置 | 流式期零开销（纯文本），finalize 一次付清 | 持续但移入 Worker，主线程近零 |
| 长回复尾部增长 | 冻结窗口固定 2 块，恒定 | live 区固定最后 1 token，近似恒定 |
| 大积压突发 | 无缓冲，可能一帧内多次渲染 | PacedMarkdown 24ms 匀速放出，天然削峰 |
| 内存 | frozenElements ReactNode 数组 | LRU html 缓存 + completedCode Map + WeakMap 状态表 |

## 四、给天枢的借鉴清单（按性价比排序）

1. **节奏层（抄 B）**：24ms 一拍 + ≤512 字符直通 + 步长自适应 + 标点吸附。约 40 行代码，与渲染引擎无关，感知提升最明显，也是"样式优化"最直接的抓手。
2. **turn-status shimmer（抄 A）**：状态行文字渐变 + `prefers-reduced-motion` 降级。纯 CSS，几行搞定"正在生成"的氛围感。
3. **未闭合 fence 快速通道（抄 B 的 `closesFence` 思路）**：检测到尾部是不完整代码块时，新字符直接追加进 pre/code，跳过整段重渲染——这是流式卡顿的最大单点来源。
4. **代码块流式高亮（抄 B，工程量大）**：Shiki stream + Worker + stable/unstable 增量 span。若天枢代码块占比高再投入；否则退而求其次用 A 的方案（流式纯文本、定稿高亮），实现成本低一个数量级。
5. **块级缓存 + 稳定 key（两家共识）**：冻结块复用渲染结果、key 取源偏移或 `key:index:mode`，保证越写越长时前面内容零重排。
6. **remend 式尾部 heal（可选，抄 B）**：想让链接/列表在流式期就正常成形再引入；接受"定稿才修正"的话可以不做。
7. **中断标记 & reduced-motion（抄 A）**：abort 后的 "stopped" 标记和无障碍降级属于完整性细节。
