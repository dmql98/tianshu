# 第一期：角色私有记忆与跨会话机制

## 1. 本期目标

一次完成单角色记忆的最终闭环：

- 什么时候触发记忆提取。
- 什么内容可以成为记忆。
- 什么时候新增、强化、修改、冲突或遗忘。
- 当前会话如何保持稳定提示词。
- 新会话如何携带该角色最新记忆。
- 组内其他角色如何按需读取被授权记忆。
- 用户如何查看、修改、拒绝和删除。

本期完成后即可独立发布角色记忆，不依赖知识库，也不需要后续破坏性重构。

## 2. 记忆归属

每条记忆必须有 owner_character_id。角色记忆默认私有，不自动变成用户全局记忆、组记忆或知识库内容。

可见性：

| visibility | 含义 |
|---|---|
| private | 只有所属角色和用户可读 |
| group | 同一角色组中拥有 memory:read_group 权限的角色可通过工具读取 |
| user | 用户显式设为跨角色共享；首版可以只保留 Schema，不默认开放 |

其他角色不得直接读取 private。组共享必须由用户策略或单条记忆明确授权。

## 3. 四级记忆

| 层级 | 内容 | 是否持久化 | 当前会话是否动态注入 |
|---|---|---:|---:|
| L0 会话工作记忆 | 当前消息、工具结果、Compaction | 是，属于 Session | 按现有会话机制 |
| L1 原子记忆 | 单个偏好、事实、决定、约束、事件、经验 | 是 | 否 |
| L2 主题记忆 | 某项目、人物或时间段的摘要与时间线 | 是，可由 L1 重建 | 否 |
| L3 Memory Snapshot | 为新会话生成的稳定角色记忆块 | 是，版本化 | 仅在会话创建时固定注入 |

L0 不写入长期记忆表。L1 是事实操作的基本单位。L2/L3 必须保存来源，不能覆盖 L1。

## 4. 记忆触发机制

不在每一轮都调用一次 LLM。采用“确定性触发器 + 异步提取器”。

### 4.1 强触发

立即创建提取任务：

- 用户明确说“记住”“以后都这样”“别再这样”“忘掉……”。
- 用户在 UI 手工新增或修改记忆。
- Agent 调用 memory_propose 工具。
- 会话即将被压缩，尚未处理的消息需要建立检查点。

明确“记住”的低敏感内容仍保存来源。明确“忘掉”直接进入删除/失效流程，不让模型自行决定是否执行。

### 4.2 批量触发

满足任一条件时处理从 last_memory_cursor 之后的消息：

- 会话正常结束或被用户关闭。
- 会话空闲达到配置时间。
- 未处理消息或 token 达到阈值。
- 用户手动点击“整理本次会话”。

### 4.3 弱信号只负责调度

规则可以识别偏好变化、长期计划、反复纠正、身份关系、稳定约束等信号，但只决定是否排队，不直接写 active 记忆。

### 4.4 幂等游标

每个 Session 保存 last_memory_cursor。提取任务幂等键由 character_id、session_id、消息范围、extractor_version 组成，重试不能重复创建记忆。

## 5. 记忆提取结果

提取器只允许返回：

- create：新建原子记忆。
- reinforce：已有记忆获得新证据。
- revise：事实或偏好发生变化。
- conflict：无法判断的新旧冲突。
- forget：用户明确要求失效或删除。
- ignore：只对当前会话有用。

候选结构至少包含 type、subject、key、content、confidence、sensitivity、visibility、valid_from、expires_at 和 source_message_ids。

以下内容默认 ignore：

- 寒暄和一次性措辞。
- Agent 自己的猜测。
- 未执行的计划。
- 工具报错或未经确认的工具输出。
- 可由当前会话上下文自然获得、但没有跨会话价值的信息。

## 6. 什么时候修改记忆

记忆不做无历史的原地覆盖。

### 6.1 Reinforce

内容一致时保留同一逻辑记忆，新增 source，并更新 last_confirmed_at 和 reinforce_count。正文不因模型换一种说法而重写。

### 6.2 Revise

同一 subject/type/key 出现明确的新值：

1. 创建新 revision。
2. 旧 revision 标记 superseded。
3. 保存 valid_to 和 superseded_by。
4. 新 revision 保存新来源。

例如“喜欢深色主题”变成“现在更喜欢浅色主题”，历史仍可查，但新会话只使用当前 revision。

### 6.3 Conflict

证据不足以判断变化时保留双方并建立 conflict。冲突内容不作为确定事实写入 L3 Snapshot，直到用户确认或后续证据解决。

### 6.4 Forget

- “不再使用”可设 expired/superseded。
- “忘掉/删除”必须从 Snapshot、检索、组共享和派生摘要中立即隐藏，再异步物理清理。

### 6.5 L2 整理

以下条件之一触发 L2 consolidation：

- 同一主题 L1 数量超过阈值。
- L1 总 token 超过角色预算。
- 会话结束且产生多个相关 L1。
- 用户手动整理。

L2 是摘要和索引，不删除原子事实。

## 7. 当前会话的冻结规则

创建 Session 时：

1. 读取角色当前已发布 L3 Snapshot。
2. 可根据首条用户消息从 L1/L2 选取少量相关补充。
3. 生成确定性的 SessionMemorySnapshot。
4. 保存 snapshot_id、content_sha256 和 memory_revision_cursor 到 Session。
5. 将 Snapshot 放在系统提示词的固定位置。

一旦会话开始：

- Snapshot 不自动改变。
- 新增、修改和删除先影响记忆库，但不重写当前会话提示词。
- 当前会话依靠最近消息知道刚产生的信息。
- 恢复同一会话仍使用原 snapshot_id。
- 每轮保持完全相同的 Snapshot 序列化、排序和空白，提升前缀缓存命中率。

用户可以显式选择“刷新当前会话记忆”，但 UI 必须提示这会改变上下文前缀。默认建议新建会话。

## 8. 新会话如何跨会话

新会话创建前先确保该角色已完成待处理记忆任务，最多等待一个短超时；超时则使用最近已发布 Snapshot，不阻断会话。

L3 Snapshot 推荐固定区块：

1. 用户稳定偏好。
2. 角色与用户的长期约定。
3. 当前有效约束和重要决定。
4. 活跃项目/关系的 L2 摘要。
5. 近期重要事件摘要。

Snapshot 有独立 token 预算，使用稳定排序，不包含生成时间、浮动分数等易变信息。长尾 L1 不全部注入，通过 character_memory_search 工具按需读取。

因此：

- 同一会话从第二轮开始可持续命中相同系统前缀缓存。
- 新会话获得最新已发布记忆。
- 不必为了跨会话把全部历史消息带过去。

## 9. 组内记忆工具

提供 group_memory_search，而不是启动其他角色。

输入：

- query
- member_ids，可选
- types，可选
- time_range，可选
- limit

处理：

1. 根据当前角色和角色组计算可访问成员。
2. 只检索 visibility=group 且当前角色有 memory:read_group 的 active 记忆。
3. 返回角色名、摘要、记忆类型、时间和来源标识。
4. 记录谁在什么时候读取了谁的哪条记忆。

工具结果进入普通 Tool Message，不进入系统提示词固定前缀。这样不会破坏前缀缓存，也不会消耗一次其他 Agent 推理。

同时提供 character_memory_search 供角色读取自己的长尾记忆。

## 10. Memory Policy

每个角色支持：

| mode | 新会话注入 | 长尾检索 | 生成候选 | 自动生效 |
|---|---:|---:|---:|---:|
| off | 否 | 否 | 否 | 否 |
| read_only | 是 | 是 | 否 | 否 |
| review | 是 | 是 | 是 | 否 |
| auto | 是 | 是 | 是 | 仅低风险 |

补充设置：

- snapshotTokenBudget
- longTermTokenBudget
- extractionTrigger
- autoApprovalThreshold
- sensitivePolicy
- defaultVisibility
- groupReadPermission

selfEvolution 完全迁出 Memory Policy，改为独立 skillMining.enabled。

## 11. 最终数据模型

本期一次建立并使用最终表：

- character_memory_policies
- character_memory_items
- character_memory_revisions
- character_memory_sources
- character_memory_conflicts
- character_memory_snapshots
- session_memory_snapshots
- character_memory_fts
- character_memory_embedding_records
- character_memory_jobs
- character_memory_access_logs

核心约束：

- 所有长期记忆拥有 owner_character_id。
- revision 不可变。
- active revision 唯一。
- Snapshot 不存无来源的新事实。
- Session 一旦绑定 Snapshot 默认不可变。
- FTS/Embedding 是可重建派生数据。

## 12. Agent Loop 接入

角色 Prompt 组装顺序中增加稳定 Memory Snapshot：

    System Rules
    Character Soul
    Character Memory Snapshot
    Goal / Plan
    Skills / Tool Guide
    Compaction
    Recent Messages

禁止：

- 每轮重新读取最新记忆并重写 Snapshot。
- 在同一会话中整份追加 memory.md。
- 记忆提取任务阻塞模型响应。
- 把其他角色记忆默认注入。

## 13. UI

角色页面：

- mode 和触发策略。
- Snapshot 预算和当前版本。
- 组共享默认策略。
- “新会话生效”的明确说明。
- 刷新当前会话记忆的缓存影响提示。

记忆中心：

- L1/L2/L3 分层查看。
- candidate、active、conflict、superseded、expired。
- 来源消息、revision 和使用记录。
- 批准、编辑、合并、解决冲突、删除、修改 visibility。

会话页面显示当前 snapshot_id，并可查看本会话固定注入的记忆。

## 14. 迁移

当前角色 memoryContent / memory.md 一次迁移为 manual_note 类型记忆，并生成首个 L3 Snapshot。

- enabled=false -> mode=off。
- enabled=true -> mode=read_only，避免升级后突然自动学习。
- charLimit -> snapshotTokenBudget。
- selfEvolution -> skillMining.enabled。

迁移后新系统成为唯一写路径。旧文件只读保留有限回滚期，不长期双写。

## 15. 验收

- 同一会话多轮请求的 Memory Snapshot 字节完全一致。
- 当前会话产生的新记忆不改变当前 Snapshot。
- 新建会话能够获得上次会话已发布记忆。
- 恢复旧会话继续使用旧 snapshot_id。
- off 模式下读取、提取、检索调用均为零。
- revise 保留旧 revision，conflict 不进入稳定 Snapshot。
- group_memory_search 只返回有授权的 group 记忆。
- 组内查询不启动其他 Agent。
- 删除后 Snapshot、FTS、向量和组工具均无法读取。
- 现有角色数据只迁移一次。
