# 0期 · 地基与进化解耦 · 可执行步骤清单

> 本文是整体施工方案（见对话中的"天枢知识体系建设·施工方案"）的第一个可执行里程碑。
> 上游设计文档：00 总体设计、01 第一期、02 第二期、03 第三期。
> 0期不交付任何用户可见功能，只补齐设计文档"假装已存在"的三套基础设施，并解开"进化系统借记忆配置位"这一处耦合，为 1/2/3 期扫清前置。

## 0. 范围与边界

**为什么先做 0期**（代码核实结论）：
- 设计 02 说知识库"复用通用 Job / EmbeddingProvider / VectorStore 基础设施"，但仓库里**三者都不存在**（全仓无 `embedding`/`vector`/`fts5`/`VectorStore`，只有 per-session 的 Promise 链）。
- 进化开关 `selfEvolution` 被塞在 `CharacterMemory` 里（`characterStore.ts:18-22`），并在 `outer.ts:420` 借记忆的位子触发（`charMeta.memory?.selfEvolution`），但它的产出是**技能**不是记忆——这就是"三者混在一起"的唯一真实现实处。

**0期做什么**：
- M0.3 进化解耦（最小、可独立交付）
- M0.2 FTS5 可用性验证 + Embedding/Vector 抽象（探针，不实现具体 Provider）
- M0.1 后台任务框架（最大依赖，1/2 期共用）

**0期不做**（明确边界，避免范围蔓延）：
- 不做记忆提取/快照/任何 01 内容
- 不做文件转换/分块/检索，02 只在 0.2 定义接口
- 不做权限矩阵/UI/审计，那是 03
- 不实现任何真实 Embedding Provider（只放接口 + lexical-only 回退）

**执行顺序**：M0.3 → M0.2 → M0.1。M0.3 与 M0.1/M0.2 互不依赖，放最前是因为它最小、能立刻验证"解耦"这个设计判断，且不会阻塞其他工作。

## M0.3 进化解耦（最先做，最小风险）

**目标**：把进化开关从 `memory` 配置对象移到顶层 `skillMining`，运行时触发点改读新字段。**不做旧数据读时兼容**——不保留永久 legacy 映射路径，旧 `memory.selfEvolution` 由一次性迁移物理清理，之后代码只认 `skillMining`。

### 步骤

- [ ] **3.1 类型拆分**
  - 涉及文件：`web/server/src/db/characterStore.ts`
  - 改动：
    - `CharacterMemory`（约 18-22 行）删除 `selfEvolution?: boolean`。
    - `CharacterRecord`（约 38 行）新增 `skillMining?: { enabled: boolean; charLimit?: number; maxEntries?: number }`。
  - 验证：`tsc --noEmit` 通过；`selfEvolution` 在 `CharacterMemory` 中消失。

- [ ] **3.2 改触发点**
  - 涉及文件：`web/server/src/agent/outer.ts` 第 420 行附近
  - 改动：`if (toolCallHistory.length > 0 && charMeta.memory?.selfEvolution)` → `if (toolCallHistory.length > 0 && charMeta.skillMining?.enabled)`。其余 `detectInsight` / `SkillGenerator` 行为不变。
  - 验证：`grep -rn "memory?.selfEvolution\|memory\.selfEvolution" web/server/src` 结果为空。

- [ ] **3.3 一次性数据迁移（非兼容层）**
  - 新增文件：`web/server/src/character/migrate-self-evolution.ts`
  - 内容：`migrateSelfEvolutionToSkillMining(): { migrated: number; skipped: number }`，遍历 `characterMetaStore.getAll()`，对含 `memory.selfEvolution` 的角色：写回 `skillMining = { enabled: record.memory.selfEvolution, ...(record.skillMining||{}) }` 并**从 `memory` 中删除 `selfEvolution` 字段**（物理清理，不是仅读时忽略）。幂等（已无该字段则 skip）。
  - 挂载：`web/server/src/app.ts` 第 177 行皮肤迁移附近调用。
  - 说明：这是**一次性**迁移，不是永久兼容层；迁移完成后 `normalizeRecord` 不再处理该字段。
  - 验证：用一条旧角色数据跑迁移，断言 `skillMining.enabled` 已写入、`memory.selfEvolution` 字段已不存在；重复调用 `skipped` 递增、幂等。

- [ ] **3.4 内置内容清理**
  - 涉及文件：`content/builtin/characters/*/character.json`、`character.pre-skill-packages.json`（仍含 `selfEvolution`）
  - 改动：一次性把内置角色的 `memory.selfEvolution` 移到 `skillMining.enabled`（或在该批内置内容 regenerate 时直接改 schema）。运行时不再依赖读时兼容，内置文件须与运行时类型一致。
  - 验证：全仓 `grep -rn "selfEvolution" content/ web/server/src` 除迁移脚本与 `skillMining` 外无残留。

- [ ] **3.5 测试**
  - 新增：`web/server/test/self-evolution-migration.test.ts`
  - 用例：①触发点改用 `skillMining`（无 `memory.selfEvolution` 引用）；②一次性迁移把值搬过去并**从 `memory` 删除字段**；③迁移幂等；④全仓无 `memory.selfEvolution` 残留。
  - **不再包含**读时 `normalizeRecord` 兼容测试（已明确不做旧数据读时兼容）。
  - 验证：`npm test --prefix web/server` 相关用例绿。

### M0.3 完成闸口
`selfEvolution` 彻底从 `memory` 对象、运行时与内置内容中退出；进化改由 `skillMining.enabled` 驱动；代码路径中**不存在**永久 legacy 映射；一次性迁移后旧字段被物理清除；新增测试全绿。

## M0.2 FTS5 可用性 + Embedding/Vector 抽象（探针）

**目标**：在设计 02 真正动手前，先确认打包的 `better-sqlite3` 带 FTS5（这是 2.5 的硬前提），并定义 `EmbeddingProvider` / `VectorStore` / 融合检索接口，真实 Provider 留到 2.5。

### 步骤

- [ ] **2.1 FTS5 可用性探针（先卡死门槛）**
  - 新增：`web/server/test/fts5-contract.test.ts`
  - 内容：通过现有 `better-sqlite3` 门面（`web/server/src/db/sqlite-db.ts`）建内存/临时库，执行 `CREATE VIRTUAL TABLE t USING fts5(body TEXT)`，插入数行，`SELECT ... WHERE t MATCH 'keyword'` 断言命中且排序合理。
  - 验证：测试通过。**若失败 = 阻塞 2.5**，需先解决 `better-sqlite3` 编译选项（启用 FTS5）或换支持 FTS5 的 SQLite 构建，再继续。在 Windows electron 打包（`desktop/electron-builder.yml`）下同样需验证。

- [ ] **2.2 EmbeddingProvider / VectorStore 接口**
  - 新增：`web/server/src/embed/embedding.ts`
  - 内容：
    - `export interface EmbeddingProvider { readonly dimensions: number; embed(texts: string[]): Promise<number[][]> }`

- [ ] **2.3 lexical-only 回退分支**

  - 验证：单测——无 Provider 时 `search` 返回 BM25 结果且 `source==='lexical'`；不抛错。

- [ ] **2.4 测试**
  - 新增：`web/server/test/embed-contract.test.ts`
  - 用例：①FTS5 探针（同 2.1）；②lexical-only 检索返回正确命中；③`RetrievalOpts` 过滤/裁剪逻辑（token 预算、limit）。
  - 验证：`npm test --prefix web/server` 相关用例绿。

## M0.1 后台任务框架（最大依赖，1/2 期共用）

**目标**：提供持久化、幂等、可重试的异步任务能力。现有只有 `web/server/src/agent/llm-call-store.ts` 的 per-session Promise 链，无法满足 1 期提取器 / 2 期转换器的"会话外异步、失败重试、重启恢复"需求。

### 步骤

- [ ] **1.1 jobs 表 Schema**
  - 涉及文件：`web/server/src/db/schema.ts`（沿用 `CREATE TABLE IF NOT EXISTS` 风格；普通表，非虚拟表）
  - 内容：
    ```sql
    CREATE TABLE IF NOT EXISTS jobs (
      id TEXT PRIMARY KEY,
      type TEXT NOT NULL,
      payload TEXT,                -- JSON
      status TEXT NOT NULL,        -- pending|running|done|failed
      owner_character_id TEXT,
      session_id TEXT,
      idempotency_key TEXT UNIQUE, -- 防重复创建
      attempts INTEGER NOT NULL DEFAULT 0,
      next_run_at INTEGER,         -- 重试退避时间点
      last_error TEXT,
      created_at INTEGER NOT NULL,
      updated_at INTEGER NOT NULL
    );
    CREATE INDEX IF NOT EXISTS idx_jobs_due ON jobs(status, next_run_at);
    ```
  - 验证：服务启动后 `jobs` 表存在；`idempotency_key` 唯一约束生效。

- [ ] **1.2 jobStore**
  - 新增：`web/server/src/jobs/jobStore.ts`
  - 方法：`enqueue(type, payload, { idempotencyKey?, ownerCharacterId?, sessionId? })`（冲突时返回已存在 job，不重复插入）、`claimDue(limit, now)`（取 `status='pending' AND (next_run_at IS NULL OR next_run_at<=now)`）、`complete(id)`、`fail(id, err, nextRunAt?)`、`getByKey(key)`、`get(id)`。
  - 验证：单测——enqueue 同 key 只建一条；claimDue 只取到期项。

- [ ] **1.3 处理器注册与执行封装**
  - 新增：`web/server/src/jobs/handlers.ts`
  - 内容：`registerHandler(type, fn)`；`execute(job)` 用 try/catch 包 `fn`，成功 `complete`，失败 `fail` 并按 `attempts` 与退避写 `next_run_at`；**以 `idempotency_key` 保证幂等**（同一 key 不会被并发 claim 两次——claim 时即置 `running` 并写事务）。
  - 验证：单测——handler 抛错后 `status='failed'` 且 `last_error` 记录；重试计数递增。

- [ ] **1.4 Worker**
  - 新增：`web/server/src/jobs/worker.ts`
  - 内容：`startJobWorker({ pollMs })`，定时 `claimDue` → `execute`；与现有 per-session 队列（`llm-call-store.ts`）**并存、互不影响**；worker 异常不能拖垮服务启动。
  - 挂载：`web/server/src/app.ts` 启动时调用 `startJobWorker()`（与皮肤迁移、`migrateSelfEvolutionToSkillMining` 同区域）。
  - 验证：服务启动后 worker 在跑（`claimDue` 被周期调用）；type=test 任务能被消费并置 `done`。

- [ ] **1.5 与 SQLite 事务边界**
  - 约定：claim/complete/fail 各自在事务内完成；handler 业务逻辑若写业务表，自行管理事务，不在 jobStore 内隐式开大事务。
  - 验证：单测模拟 handler 中途失败，断言 job 状态正确且业务表未留下半成品（视具体业务表而定，本期仅验证 job 侧）。

- [ ] **1.6 测试**
  - 新增：`web/server/test/jobs.test.ts`
  - 用例：①enqueue 幂等（同 key）；②claimDue 只取到期；③成功→done；④失败→failed + 重试退避；⑤worker 端到端消费 type=test。
  - 验证：`npm test --prefix web/server` 相关用例绿。

### M0.1 完成闸口
`jobs` 表随服务创建；enqueue 幂等、失败可重试、重启可恢复；worker 启动不阻塞服务；1/2 期可直接 `enqueue(type='memory_extract'|'knowledge_convert', ...)` 复用本框架。

## 风险与回滚

| 风险 | 对策 / 回滚 |
|---|---|
| FTS5 不在打包 SQLite 中 | 2.1 探针先卡死；失败则升级 `better-sqlite3` 编译或换构建，复测后再进 2.5 |
| Job worker 与现有 per-session 队列冲突 | 1.4 明确并存、独立实现；worker 异常隔离 |
| 3.3 一次性迁移是唯一"破坏性"步骤 | 有限回滚期：保留 down 脚本（skillMining→memory.selfEvolution 还原）；回滚窗口内可逆向 |
| 内置内容仍含 `selfEvolution` 字段 | 3.4 一次性清理内置文件，使其与运行时类型一致 |
