# 天枢知识库三期实施方案

> 基于 NomiFun Desktop 知识库架构分析，适配天枢 Node.js/TypeScript 技术栈。
> 前置文档：`00-知识体系总体设计.md`、`02-第二期-独立文件知识库.md`

---

## 0. NomiFun 架构参考摘要

NomiFun 的知识库是一个成熟的 Rust 实现，核心设计如下：

### 数据流

```
用户上传文件 → 存储原件 → 转换为 Markdown → 分块(chunk) → 索引(FTS/向量)
                                                         ↓
Agent 调用 knowledge_search → 检索 top_k 结果 → 返回 {handle, snippet, score}
Agent 调用 knowledge_read   → 通过 handle 解码 → 读取完整文档
```

### 核心搜索算法（`score_md`）

```
评分规则（纯本地关键词模式）：
  路径/标题 完整匹配 query  → +8
  正文 完整匹配 query       → +5
  每个 term 命中路径        → +4
  每个 term 命中标题        → +3
  每个 term 命中正文 TF     → +min(tf, 5)

片段提取（best_snippet）：
  取第一个命中 query 或 term 的行，截断到 200 字符
```

### 文档 Handle 机制

```
kdoc_ + base64({kb_id}\x1f{rel_path})
→ 不透明令牌，模型只传不解析，避免路径拼接错误
```

### 存储结构

```
元数据：SQLite（knowledge_bases / knowledge_entries 表）
文件内容：文件系统（每个知识库 = 一个目录）
搜索缓存：内存 HashMap，key=PathBuf，value={mtime_ms, content, heading, bytes}
```

## 2. P1：纯 MD 文件 + 检索 Tool

### 2.1 目标

**会话级知识库挂载 + 按需注入检索工具**。

### 2.6 核心算法（TypeScript 移植）

#### 搜索流程（作用域限定版）

```
1. 从 ctx.knowledgeBases 获取当前会话挂载的知识库 ID 列表
2. 从 bases.json 加载这些知识库的 rootPath
3. 遍历每个 rootPath，递归扫描目录，收集所有 .md 文件
4. 读取文件内容（UTF-8），提取第一个 heading
5. 对每个文件执行 score_md(query, terms, relPath, heading, content)
6. 按 score 降序排列，取 top_k
7. 对每个命中提取 best_snippet（含行号）
8. 编码 handle 返回
```

#### `score_md` — 评分函数

```typescript
function scoreMd(
  relPath: string,
  heading: string,
  content: string,
  queryLc: string,
  terms: string[]
): [number, string, number, number] | null {
  const pathLc = relPath.toLowerCase()
  const headingLc = heading.toLowerCase()
  const contentLc = content.toLowerCase()
  let score = 0

  // 完整匹配 query
  if (pathLc.includes(queryLc) || headingLc.includes(queryLc)) score += 8
  if (contentLc.includes(queryLc)) score += 5

  // 逐 term 匹配
  for (const t of terms) {
    if (pathLc.includes(t)) score += 4
    if (headingLc.includes(t)) score += 3
    const tf = contentLc.split(t).length - 1  // 出现次数
    score += Math.min(tf, 5)
  }

  if (score === 0) return null

  // 提取最佳片段
  const { text: snippet, startLine, endLine } = bestSnippet(content, queryLc, terms)
  return [score, snippet, startLine, endLine]
}
```

#### `best_snippet` — 片段提取（含行号）

```typescript
function bestSnippet(
  content: string,
  queryLc: string,
  terms: string[]
): { text: string; startLine: number; endLine: number } {
  const lines = content.split('\n')
  const hitLineIdx = lines.findIndex(line => {
    const l = line.toLowerCase()
    return l.includes(queryLc) || terms.some(t => l.includes(t))
  })
  const idx = hitLineIdx >= 0 ? hitLineIdx : 0
  const line = lines[idx]?.trim() ?? ''
  const truncated = line.length > 200 ? line.slice(0, 200) + '…' : line
  return { text: truncated, startLine: idx + 1, endLine: idx + 1 }
}
```

#### `query_terms` — 分词

```typescript
function queryTerms(queryLc: string): string[] {
  // 简版：按空白分词，过滤单字符
  return queryLc.split(/\s+/).filter(t => t.length >= 2)
}
```

#### `encode_handle` / `decode_handle` — Handle 编解码

```typescript
function encodeHandle(kbId: string, relPath: string): string {
  const raw = `${kbId}\x1f${relPath}`
  return 'kdoc_' + Buffer.from(raw, 'utf-8').toString('base64url')
}

function decodeHandle(handle: string): { kbId: string; relPath: string } | null {
  if (!handle.startsWith('kdoc_')) return null
  try {
    const raw = Buffer.from(handle.slice(5), 'base64url').toString('utf-8')
    const sep = raw.indexOf('\x1f')
    if (sep < 0) return null
    return { kbId: raw.slice(0, sep), relPath: raw.slice(sep + 1) }
  } catch {
    return null
  }
}
```

### 3.5 转换器接口

```typescript
interface Converter {
  name: string                          // 'pdf' | 'docx' | 'xlsx' | ...
  inputExtensions: string[]             // ['.pdf']
  convert(inputPath: string, outputPath: string): Promise<ConvertResult>
}

interface ConvertResult {
  ok: boolean
  outputPath?: string
  error?: string
  metadata?: {
    pageCount?: number
    sheetCount?: number
    anchorMap?: SourceMapEntry[]         // 来源映射（页码/行号）
  }
}

interface SourceMapEntry {
  mdLine: number
  sourcePage?: number
  sourceSheet?: string
  sourceSlide?: number
}
```

### 3.6 文件生命周期

```
1. 用户上传文件 → 存储到 originals/{kbId}/
2. 识别扩展名 → 查找匹配的 Converter
3. Converter 生成 normalized/{kbId}/{name}.md + source-map
4. 更新 bases.json 中的文档状态（pending → indexed）
5. 失败时保留状态为 error，记录错误信息
```

## 4. P3：向量知识库

### 4.1 目标

实现分块 → 向量化 → 混合检索（BM25 + 向量 + RRF 融合），达到企业级 RAG 检索质量。

### 4.2 核心组件

| 组件 | 技术选型 | 说明 |
|------|---------|------|
| **分块引擎** | 自研 Markdown AST 分块 | 6 种预设（General/QA/Book/Laws/Semantic/Separator） |
| **向量存储** | SQLite + `sqlite-vec` 扩展 | 本地零基建，嵌入 SQLite |
| **Embedding** | 远程 API（OpenAI `text-embedding-3-small`） | 可选本地 `all-MiniLM-L6-v2` via `@huggingface/transformers` |
| **Reranker** | 远程 API（Cohere / Jina） | 可选，提升精度 |
| **混合检索** | BM25 + 向量相似度 + RRF 融合 | 同 NomiFun 的 candidate → rerank 流程 |

### 4.3 分块策略

Demo 中的 6 种预设对应不同文档类型：

| 预设 | 策略 | 适用场景 |
|------|------|---------|
| General | 按分隔符和长度切分 | 大多数普通文档 |
| QA | 优先抽取问题-回答结构 | FAQ、题库 |
| Book | 强化标题识别并层级合并 | 教材手册 |
| Laws | 按法条层级组织合并 | 制度规范 |
| Semantic | 嵌入聚类语义切分 | 通用语义文档 |
| Separator | 命中分隔符即切分 | 结构化文本 |

## 7. 关键设计决策

### 7.1 存储选型

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| JSON 文件 | 零依赖、简单 | 并发写不安全、查询慢 | **P1 采用** |
| SQLite | 查询快、并发安全 | 需要引入依赖 | **P3 采用**（chunks + embeddings） |

### 7.2 检索选型

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 纯关键词（TF-IDF） | 零基建 | 语义理解差 | **P1 采用** |
| 向量（Embedding） | 语义理解好 | 需要 API/模型 | **P3 采用** |
| 混合（BM25 + 向量 + RRF） | 兼顾两者 | 复杂度高 | **P3 采用** |

### 7.3 前端 UI

| 阶段 | UI 策略 |
|------|---------|
| P1 | RightPanel 会话级挂载区（对标帮手，复用 helper-grid 样式）+ `knowledge_manage` tool |
| P2 | 可选：简化版三栏管理页（知识库列表/文档列表/预览） |
| P3 | 检索配置面板 + 检索调试 Tab |

### 7.5 会话挂载 vs 全局默认注入

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 全局默认注入 knowledge_search | 简单 | 所有会话都有工具，浪费 token；模型可能误搜 | ❌ 不采用 |
| 会话级挂载（同帮手模式） | 精确控制；按需注入；作用域限定 | 需要改 agent loop | ✅ **采用** |
| 角色级绑定 | 与角色关联 | 灵活性差；跨角色共享困难 | ❌ 不采用 |

会话挂载模式的关键优势：
- **作用域安全**：`knowledge_search` 只能搜索当前会话挂载的知识库，不能越权
- **按需注入**：未挂载时不注入工具，节省 token
- **灵活性**：同一角色在不同会话可以挂载不同知识库
- **一致性**：与现有帮手（targets）和授权工作区（workspaces）完全同构

### 7.4 与现有 Memory 系统的关系

```
Memory（角色记忆）    ←→  独立系统，有独立表/工具/UI
Knowledge（文件知识库） ←→  独立系统，有独立表/工具/UI

Agent 通过 tool 按需检索：
  - character_memory_search → 读角色自己的长尾记忆
  - group_memory_search    → 读同组授权记忆
  - knowledge_search       → 读文件知识库

禁止：
  - knowledge_chunk 写入 memory_item
  - 知识库内容自动注入系统提示词
  - 两个系统共用事实表
```
