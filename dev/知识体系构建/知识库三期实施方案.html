0 · NomiFun 架构参考摘要

NomiFun 的知识库是成熟的 Rust 实现，为天枢的实现提供了可直接移植的算法与机制。

数据流

用户上传文件 → 存储原件 → 转换为 Markdown → 分块(chunk) → 索引(FTS/向量)
                                                         ↓
Agent 调用 knowledge_search → 检索 top_k 结果 → 返回 {handle, snippet, score}
Agent 调用 knowledge_read   → 通过 handle 解码 → 读取完整文档

核心搜索算法（score_md）

命中位置加分
路径/标题 完整匹配 query+8
正文 完整匹配 query+5
每个 term 命中路径+4
每个 term 命中标题+3
每个 term 命中正文 TF+min(tf, 5)

片段提取（best_snippet）：取第一个命中 query 或 term 的行，截断到 200 字符，并返回行号。

文档 Handle 机制

kdoc_ + base64({kb_id}\x1f{rel_path})
→ 不透明令牌，模型只传不解析，避免路径拼接错误

存储结构

数据存储
元数据SQLite（knowledge_bases / knowledge_entries 表）
文件内容文件系统（每个知识库 = 一个目录）
搜索缓存内存 HashMap，key=PathBuf，value={mtime_ms, content, heading, bytes}

2.6 核心算法（TypeScript 移植）

score_md — 评分函数

function scoreMd(relPath, heading, content, queryLc, terms) {
  const pathLc = relPath.toLowerCase(), headingLc = heading.toLowerCase(), contentLc = content.toLowerCase()
  let score = 0
  if (pathLc.includes(queryLc) || headingLc.includes(queryLc)) score += 8
  if (contentLc.includes(queryLc)) score += 5
  for (const t of terms) {
    if (pathLc.includes(t)) score += 4
    if (headingLc.includes(t)) score += 3
    const tf = contentLc.split(t).length - 1
    score += Math.min(tf, 5)
  }
  if (score === 0) return null
  return [score, ...bestSnippet(content, queryLc, terms)]
}

encode_handle / decode_handle — Handle 编解码

function encodeHandle(kbId, relPath) {
  return 'kdoc_' + Buffer.from(`${kbId}\x1f${relPath}`, 'utf-8').toString('base64url')
}
function decodeHandle(handle) {
  if (!handle.startsWith('kdoc_')) return null
  const raw = Buffer.from(handle.slice(5), 'base64url').toString('utf-8')
  const sep = raw.indexOf('\x1f'); if (sep < 0) return null
  return { kbId: raw.slice(0, sep), relPath: raw.slice(sep + 1) }
}

7.1 存储选型

选项优点缺点结论
JSON 文件零依赖、简单并发写不安全、查询慢P1 采用
SQLite查询快、并发安全需引入依赖P3 采用（chunks+embeddings）

7.2 检索选型

选项优点缺点结论
纯关键词（TF-IDF）零基建语义理解差P1 采用
向量（Embedding）语义理解好需 API/模型P3 采用
混合（BM25+向量+RRF）兼顾两者复杂度高P3 采用

7.3 前端 UI

阶段UI 策略

7.4 与现有 Memory 系统的关系

Memory（角色记忆）    ←→  独立系统，有独立表/工具/UI
Knowledge（文件知识库） ←→  独立系统，有独立表/工具/UI

Agent 通过 tool 按需检索：
  - character_memory_search → 读角色自己的长尾记忆
  - group_memory_search    → 读同组授权记忆
  - knowledge_search       → 读文件知识库

禁止：
  - knowledge_chunk 写入 memory_item
  - 知识库内容自动注入系统提示词
  - 两个系统共用事实表

7.5 会话挂载 vs 全局默认注入

方案优点缺点结论
全局默认注入 knowledge_search 简单 所有会话都有工具，浪费 token；模型可能误搜 ✗ 不采用
会话级挂载（同帮手模式） 精确控制、按需注入、作用域限定 需要改 agent loop ✔ 采用
角色级绑定 与角色关联 灵活性差；跨角色共享困难 ✗ 不采用

会话挂载模式的关键优势：

  • 作用域安全：knowledge_search 只能搜索当前会话挂载的知识库，不能越权
  • 按需注入：未挂载时不注入工具，节省 token
  • 灵活性：同一角色在不同会话可挂载不同知识库
  • 一致性：与现有帮手（targets）和授权工作区（workspaces）完全同构
