天枢会话体验差距报告
工具调用展示 · 问答闭环 · 上下文压缩 —— 附「问答后不显示」Bug 根因

一、P0 · 「问答结束后不显示，要刷新才出来」根因

结论先行：这不是流式问题，是事件缺失 + 无乐观更新的双重缺口。用户回答被服务端静默写库，前端全程无感知。

根因 1（主因）：用户的回答入库时没有发出任何事件

POST /runs/:id/inputs（routes/runs.ts）应答后调用 createResumedRun({ createUserTurn: true })，它在 run-resume-service.ts:147 直接 messageStore.addMessage(role:'user') 把回答写进 messages 表——全程没有 publish 任何事件。前端的 AskUserDialog 提交成功后只做 clearAskUser() 关弹窗，也不做本地乐观插入。于是：回答气泡不出现，直到某次 fetchSessionMessages（刷新/重进）才从库里读出来。

根因 2（次因）：恢复 run 的认领只靠 run.started 单点，且 run.queued 被显式忽略

恢复 run 带 trigger: 'user_input'，而客户端 handleAutoSuccessorQueued 只认领 trigger === 'auto_limit' 的 run.queued——user_input 的 run.queued 直接落空。后续只能等 loop-engine 发出的 run.started 兜底认领。一旦这条事件因 SSE 抖动 / IPC 重连丢失，整个后续回复都不会实时出现（resumeActiveRun 只在切换会话和手动刷新时触发），表现同样是「刷新才出来」。

当前事件时序（红色 = 断点）

  1. 模型调 ask_user → 服务端 checkpoint + emit ask_user → 前端弹 AskUserDialog ✓
  2. 循环 break → run 正常收尾 → emit run.completed（旧 run）→ 前端清 activeRunId ✓
  3. 用户提交回答 → POST /runs/:id/inputs → messageStore.addMessage(回答) —— 无事件，前端不知道
  4. emit run.queued (trigger=user_input) → 前端 handleAutoSuccessorQueued 只认 auto_limit，忽略
  5. 恢复 run 执行 → emit run.started → 前端认领（唯一兜底，丢了就全断）
  6. message.delta 流式追加 → 后续回复理论上能实时显示（依赖第 5 步成功）
  7. 用户回答气泡 → 永远不实时显示，等刷新拉库

修复建议（双保险）

层改法效果
服务端createResumedRun 落库用户回答后，补发一条 durable 事件（如 message.created，带 message_id / role / content），并加入客户端 ALL_KNOWN_EVENTS；同时把 handleAutoSuccessorQueued 放宽到也认领 trigger === 'user_input'权威修复：重连重放（fetchRunEvents）也能恢复，任何传输通道一致
客户端AskUserDialog.handleSubmit 成功后立即把回答作为 user 消息乐观插入 sessions[id].messages（带临时 id）零延迟反馈：点下「回答」立刻看到自己的气泡，不等任何往返
附带发现：客户端 switchSession 对已有消息的会话早退不重新拉取（只 resumeActiveRun），所以「切走再切回」并不能修复数据，只有整页刷新或点刷新按钮才行——这与用户「退出去刷新才显示」的体感吻合，也值得顺手修掉（切回时若该会话 updated_at 比本地新则静默重取一次）。

二、工具调用展示对比

这是差距最大的一块。天枢目前是「一行文本标签」，两个参考项目都是「按工具定制的结构化卡片体系」。

天枢现状

  • 展开后 tool_output 纯文本直出，无高亮、无 diff、无虚拟滚动
  • iconByTool 只映射 6 种工具，其余全部回落 bash 图标

  • CodeBlock / JsonBlock 统一承载输出，带截断与复制
  • 未知块回落 JsonBlock（label + truncatedLabel），永不空白

天枢落地建议（工具调用）

引入 opencode 式 ToolRegistry：保留现有 tool.started / tool.completed / tool.output 事件（数据已够），只重做展示层——

  • 骨架：可折叠卡片 = 头部（图标+工具名+参数摘要+状态点+耗时）+ 展开体（结构化输入/输出）
  • 优先定制 4 个：bash（输出终端样式 + 流式追加已有）、read/grep/glob（参数表格化）、write/edit（diff 视图，可引 prism/shiki 轻量方案）
  • 兜底：GenericTool 渲染 JSON.stringify(input, null, 2)，错误态红卡片，杜绝现在的「原始字符串平铺」
  • tool_input 是 JSON 字符串就先 parse 再展示，parse 失败才原文兜底

三、问答（ask_user）交互对比

天枢已有可用的 checkpoint 机制（这部分骨架是好的），差距在「闭环后的呈现」与「历史可见性」。

能力天枢现状deepseek-harnessopencode-dev

四、上下文压缩展示对比

天枢压缩能力存在（手动 /compact + run.compacted 事件），但 UI 上只有一个角落标记，会话流里毫无痕迹。

天枢现状

右栏一行小字

  • run.compacted → 仅 session.compacted = true
  • RightPanel 渲染「⚠ 会话已压缩」10px 小字，仅此而已
  • 手动压缩成功 → toast「已压缩至 N tokens」，转瞬即逝
  • 会话流内无任何压缩标记：用户不知道历史在哪被截断、模型从哪开始"失忆"
opencode-dev

会话流内分隔线

  • compaction 是一种 message part，渲染为时间线中的 MessageDivider（"Context compacted" 居中分隔线）
  • 压缩点之上是旧历史、之下是新上下文，位置语义直观
  • 实现约 10 行——成本极低，收益是用户能感知"模型记忆边界"
deepseek-harness

可展开的压缩检查点卡片（最完整）

  • CompactionItem：默认收起的一行标记，明确表述"模型从这里停止看到更早历史"，不替换历史只遮蔽
  • 摘要行显示遮蔽条目数 + token 数（shadowedItemCount / shadowedTokenCount）
  • 展开可看压缩摘要全文（来自 compaction/summary 事件）；摘要缺失时禁用展开而非空白
  • CompactionCommandCard 单独承载 /compact 命令的 running 态与结果

天枢落地建议（压缩）

分两步走，第一步当天可完成：

  • 第一步（抄 opencode）：run.compacted 到达时往 messages 插入一条 role:'system-notice' 类消息（或前端虚拟标记），MessageList 渲染为居中分隔线「── 上下文已压缩 ──」。持久化侧让压缩事件落 messages 表（带 marker 类型），重进会话也能看到。
  • 第二步（抄 harness）：分隔线可点击展开，显示压缩摘要与"遮蔽了 N 条 / M tokens"；服务端 compaction 时把 summary 与计数放进事件 payload。

六、轨迹页与对话改造的联动分析

轨迹页是纯读模型：GET /:id/trajectory = runs + messages 全量 + run_events（durable 事件）+ llm_calls 快照，无自有状态。对话侧改对了，轨迹自动跟上；但下面四处需要显式补齐。

对话侧改造项轨迹是否自动同步说明 / 需要补什么
问答回答入流
(P0 · message.created 事件)		 ✓ 自动同步 轨迹内容行直接读 messages 表，回答落库后轨迹天然多一行 user 行。唯一要求：新事件必须走 publishRunEvent（durable）——这正好是 P0 修复方案本身，两个页面共享同一份修复。
问答问题侧入流
(P0 · assistant 提问消息)		 ✓ 自动同步 提问消息入 messages 表后轨迹自动成对显示。但建议顺手把 TrajectoryRow 的 user/assistant/tool 三类扩展出 ask 对语义标记，让详情面板能按「问答对」展示（现在是平铺行，看不出配对关系）。
压缩分隔线入流
(P2 · 时间线 marker)		 △ 半自动 轨迹已有生命周期事件条「上下文压缩」(run.compacted → LIFECYCLE_LABEL)，但只有一行文字，没有摘要内容。服务端 compaction 后 summary 存在 sessions.compaction_summary 字段里，事件 payload 里没有带上——补上 payload 即可让轨迹的压缩事件条可展开看摘要。
工具卡片体系
(P1 · ToolRegistry)		 — 不依赖 轨迹的工具行有自己的展示（参数/结果/指标/原始 tabs），与聊天侧 ToolRegistry 独立，互不影响。

轨迹侧独立优化点（不依赖对话改造，顺路可做）

  1. run.compacted 事件 payload 补摘要数据 —— loop-engine.ts 三处 emit 处把 { summary, shadowedTokens } 带上；trajectory.ts 的 LIFECYCLE 条渲染时支持展开。改动极小，收益直接
  2. ask_user 问答对在轨迹中配对显示 —— 现在 ask_user 是一条 warn 色事件条 + 一条 tool 行([asked user])，用户回答是另一条独立 user 行，三者散落在时间线各处。buildTrajectory 时把 checkpoint 事件、tool 行、回答行聚合成一个「问答对」组。
  3. message.created 加入 TRAJECTORY_REFRESH_EVENTS —— 新增 durable 事件后记得加进这个订阅列表，否则轨迹要等到下一条 run.* 事件才刷新（有 400ms 节流兜底，影响小但值得对齐）。
架构判断：天枢的轨迹页设计是对的——纯读模型 + 单一事实源（messages / run_events / llm_calls），参考项目 deepseek-harness 也是这个思路（trajectory-assistant-definition 等全部从 snapshot store 派生）。这意味着对话侧的所有改造不需要为轨迹做第二份数据写入，只要保证：① 新消息走 durable 事件；② 压缩/问答的结构化信息放进事件 payload。轨迹自动受益。
