1TabTin 项目全貌

1.1 是什么 / 解决什么问题

TabTin（tabtin.com / github.com/tabtin-ai/TabTin，AGPL-3.0-only，版权 Shanghai Mofan Technology Co., Ltd.）是一个开源的人与 Agent 协作平台，当前处于 Public Preview（公开预览），本次研究的快照为 1.1.2 / 1.1.3（含多个 session-share 修复 commit）。

它的核心命题是：「一个人已经完成的工作，能不能直接成为下一位同事的起点？」——解决的是 AI 提高个人产出后、团队效率没有同步提升的问题（重复调研、上下文与判断依据丢失、Token 重复消耗、方法难复用、结果责任不清）。

产品理念建立在五个原则上：过程可见、权限可控、结果可检查、工作可交接、责任有人承担。核心概念模型：

Organization（组织 / 租户边界，成员+资源+配置）
├── Workspace（成员的私有执行现场：工作根+文件+终端+Skill+Checkpoint）
├── Agent（AI 参与身份：角色+规则+模型+Skill+记忆，不代表执行位置）
├── App（文档/表格/终端/浏览器/消息/演示 等一等协作应用）
└── Device（实际执行环境：Electron / Daemon / 云实例 / 移动端 / IoT）

1.3 核心架构与数据模型（协作/共享/存储相关）

① 身份与租户（users 包）

模块职责关键点（源码核实）
users/auth注册/登录/JWT/验证码/OAuth自定义 User（手机号/邮箱/昵称/头像）；JWT access 1h + refresh 7d；邀请码门禁中间件 invite_gate_middleware；飞书/GitHub OAuth；短信/邮件验证码（AUTH_RATE_LIMITS 限流）
users/membership会员等级MembershipTier：free/basic/pro/enterprise，每档带配额（表格数/文档数/存储字节/月 LLM credits/席位）；OrganizationMembership 关联组织
users/wallet点券钱包credits 精确余额 + 预扣冻结机制（LLM 调用前冻结、调用后结算释放，WAL-07）
services/billing计费BillingSummary/Policy/Entitlement/Invoice；组织级用量仪表盘；entitlement 与会员等级同步

② 组织 / 空间 / 设备 / 权限（tabtinspace）

  • Organization：type=personal（注册自动创建、唯一）| team（可邀请协作）；owner、settings、生命周期墓碑（deleting）。
  • Device：执行设备（electron/daemon/cloud，role=control）与能力设备（mobile/iot，role=data）；指纹指纹 fingerprint + machine_key（sha256(machineId+profile)）硬件锚定；capabilities JSON 决定 Space 工具域；online/busy/offline 状态。
  • Space / SpaceMembership：协作容器（bot/group/dm/team），成员关系；SpacePermission(ResourcePermission) 统一资源 ACL。
  • RemoteServer / SecureCredential：SSH 远程服务器 + 加密凭据（挂在 Device 下）。
  • ContextItem：把云文档/表格/浏览器采集/文件统一纳入 Workspace/Project 资源索引。
  • ResourcePermissionService：统一 grant/revoke/list，subject=用户/组织，role=viewer/editor/admin/owner。

③ 会话共享（chat/conversation —— 用户最关心的"协作模式"核心）

这是 TabTin 最能直接借鉴给天枢的部分。SessionShare 模型（chat_session_share）把一条 Agent 会话按三档能力授权给同一组织的另一个用户：

档位能力语义（源码注释核实）
查看（基础）只读grantee 进入 owner 的同一个会话（组织内全量透明），读端点 + WS 实时流全量可见（过程/工具/产物）。
fork（叠加位 can_fork）抄写把会话快照（正文+工具名+附件引用）抄写成接收人自己的 Agent × Workspace 新会话（session_materializer）。
对话（叠加位 can_chat）发言驱动grantee 经 shared-chat 端点在本会话发言驱动 Agent；执行在 owner 设备、费用归 owner、审批仅 owner；每次发言写 chatted 审计。
  • 安全边界：不共享执行现场（workspace/device/目录）；_get_session_with_shared_access 默认关闭共享放行，只有显式 include_session_share=True 才开第 3 分支。
  • 生命周期：pending（意图记录，不授读权）→ 投递确认 + 接收方加入 → active；revoked 停止；version + access_epoch 使旧实时订阅立即失效。
  • 资源级追溯：SessionShareResourceGrant 记录共享带来的云文档/表格 ACL 来源（停止共享只回收它带来的权限，不误伤其他渠道权限）；SessionShareResourceSyncJob 异步同步消息产物 ACL。
  • 审计：SessionShareEvent（append-only）：created/updated/viewed/forked/chatted/revoked，回答「谁何时授予/改权/看过/fork/撤销」。
  • IM 投递：共享卡走 tabchat（组织内 IM）会话分享，卡片契约 session_share / v2，delivery_status pending→confirmed；另有「交接包」（在团队会话发送目标/进展/风险并引用会话与资源）。
  • 跨组织隔离：grantee 必须是同 Organization 成员（测试 test_cross_org_grantee_rejected 验证）；分享给自己拒绝。

④ 实时协作（collab-core + collab-live + centrifugo）

  • collab-core（前端）：Provider 状态机、重连、IndexedDB（y-indexeddb）离线缓存、useOfflineReplay 离线回放、sharding、同步模式降级（collab → legacy，reason 枚举含权限受限/连接挂起等）。
  • collab-live（Node 服务）：Hocuspocus + Y.js WebSocket 服务器，permission-guard / force-close / connection-limiter / redis 扩展；apply-ops 命令服务（Y.Doc-first）。
  • WS 网关：contracts/asyncapi/ws-gateway.yaml 定义 GatewayEnvelope，角色体系（electron/mobile/daemon/admin/channel/backend）+ topic 能力矩阵 + 关闭/错误码。
  • Centrifugo：IM 与事件推送的 WS 网关（v6），Django centrifugo_proxy 签发 token。

⑤ 共享模式（tabdoc / tabdata 公开分享）

  • DocumentShare：share_type（link / organization / password…）；可选密码（set_password 用 Django hasher）；外链 /api/tabdoc/shared/{share_id}：get_shared_meta / verify_password / get_shared_content / collab-token（给外链访客签发实时协作 token） / image-assets；评论（DocumentShareComment）。
  • 组织分享：share_type=organization 时必填 organization_id；也支持组内可见性。
  • TabData 同样有 /shared/ 系列公开分享端点 + 表单（api_form）。

⑥ 云存储（services/oss + oss-client + storage-manager）

  • OSS 上传链路：oss-client 实现 presign → PUT → confirm 三步直传；秒传（computeFileHash → presign 传 file_hash）；分片上传接口；onProgress；pending-confirm 断点续传（本地持久化待确认队列 + 重试）。
  • FileRecord / FileUsage：统一文件索引 + 用量（含秒传命中标记 instant）。
  • TabFiles：裸文件作为 ContextItem（tabfiles）纳入 Workspace / Project / Organization 资源体系，上传、从聊天归档、下载 URL。
  • 本地存储管理：storage-manager 用「Bucket 模型」统一管理各模块本地数据（对话历史/Checkpoint/业务 App/浏览器/媒体/缓存/系统），D-4 四档清理 Affordance（L1 一键清/L2 半缓存提示/L3/L4 输入名字二次确认），运行时强制校验。
  • 版本历史：collab 的 VersionHistory 通用表：全量快照 + 增量 diff 混合版本链（zlib 压缩 blob）、editor_type=user/agent/system、命名版本/置顶、TTL 降采样；ChangeLog 通过 agent_run_id 关联同一轮 Agent 的跨模块变更。

⑦ 部署 / 分版

edition.py：saas / community 双版本。Community Server 只监听本机、Docker 数据卷本地存储、默认关 Sentry/更新、SMS/EMAIL/OSS 全 disabled 或 local、无邀请码。bootstrap（community_bootstrap）幂等创建 Community 会员档（全功能本地权益）。

1.5 工作应用：文件 / 表格 / 浏览器（TabTin 三大生产力模块）

本节重点：TabTin 不止是「聊天 + 共享」，它的差异化还体现在三个一等工作应用——文件（TabDoc/TabFiles）、表格（TabData/SmartSheet）、浏览器（Browser/Crawlspace）。这三个模块都深度集成了 Agent（Agent 可直接读写）、协作（Y.js 实时）与权限（ACL/共享），是「人和 Agent 操作同一份在线结果」理念的载体。

① 文件系统：TabDoc（文档）+ TabFiles（云盘文件）

TabDoc —— 在线文档（Airtable/Notion 式文档编辑器）

  • 编辑器：packages/doc-editor —— TipTap/ProseMirror 扩展（canvas-block、html-block、tabdata-block 内嵌表格块）；createCollaborativeDocExtensions（协作扩展）。
  • 后端：tabdoc app（api.py / api_share.py / services/document_service.py）——文档 CRUD、revision、import markdown、docx/markdown 互转（exchange_service）、搜索（search_service）、评论（comment_service）。
  • 版本：revision + collab VersionHistory 版本链。
  • 共享：DocumentShare 外链 + 密码 + 组织共享 + collab-token + 评论（见 1.4 ⑤）。
  • 本地解析：local-docparse（PDF/Word/Excel 本地文本提取，80% 场景不依赖云端，20% 降级云端 VLM）；file-pipeline（epub/pptx/image/local-doc 解析器 + FileResolver 统一路由）。

TabFiles —— 云盘文件

  • tabfiles_service.py：裸文件作为 ContextItem（item_type='tabfiles'）纳入 Workspace / Project / Organization 资源索引。
  • 上传/从聊天归档/下载 URL；OSS FileRecord + FileUsage（秒传 instant 标记）。
  • 文件版本：file-history-core（FileHistoryService：备份 + 回滚 rewind + 指纹 diff）。
  • office-preview-runtime / media-capabilities（音视频/图片能力探测）。

② 表格：TabData + SmartSheet + TableEngine（多维表格/数据库）

数据模型（tabdata）

  • Table：TrashableModelMixin + ContextSyncMixin；source_type=native（本地）/ mirror（镜像同步外部）/ proxy（实时代理查询外部数据源）；RLS 行级安全（rls_enabled / rls_force + RowPolicy）。
  • TableField：22 种字段类型 —— text/long_text/number/percent/currency/rating/select/multi_select/checkbox/date/created_time/last_modified_time/url/email/phone/user/created_by/last_modified_by/attachment（附件）/link（关联）。
  • TableRecord：record_version_seq（全局单调递增版本序列）+ record_delete_version —— 为增量同步设计。
  • TableView：7 种视图 —— grid / kanban / calendar / gallery / list / flashcard / form。
  • TablePermission(ResourcePermission) + 行级 RowPolicy（RLS）。

引擎 / 同步 / 协作

  • table-kernel：领域内核（field/record/view/table 应用层 + orchestration + specs）——前后端共享的表格领域逻辑。
  • table-kernel-pglite：PGlite（浏览器内 Postgres）本地副本 + 增量同步：since_version + record_version_seq 拉 delta；outbox（__tabtin_sync_outbox 变更发件箱） + OutboxFlusher（按 action 分组推送 + 独立 ack/fail + 幂等重试）；DeltaApplier（upsert/delete + ghost 清理）；fullReconcile。这是"离线可用 + 增量同步"的教科书实现。
  • table-engine：前端数据网格引擎（useIncrementalSync / useDataGridSyncRuntime / useTableEventStream / useTableCollaboration）+ Y.js collab 桥（ydoc-schema / useDataGridCollabBridge）。
  • smartsheet：SmartSheet 类 + CellManager/ViewManager/ImportExportManager + StorageAdapter（可插拔本地/远端存储）。
  • Agent 直连：api_agent_sql（POST /spaces/{id}/sql/query|execute|catalog）——Agent 用 SQL 读写表格；api_open（Open API：RLS policy / webhook / import template / PDF 导出）。
  • 协作服务：CollabService（table_changes_to_apply_ops → collab-live 应用 op）、TableEventService（publish_table_update 广播到 live）、share_service（invite_collaborators：幂等 + 通知去重 + 组织成员过滤 + 权限变更/降级触发 collab revoke）。

③ 浏览器：BrowserCore + Crawlspace + 反检测（Agent 浏览/采集）

BrowserCore —— Agent 浏览器控制

  • BrowserToolImpl：executeAct（14 种动作：click/fill/scroll/drag/type/keyPress/hover/dblclick/upload/select…）/ executeObserve / requestSnapshot；循环检测（ActionLoopDetector）、限流、重试。
  • CDPConnectionManager：连接池 + 策略升级（task-bound / keep-alive）+ 驱逐（inFlight 保护）。
  • AccessStrategyService：拦截信号分类（cloudflare / rate_limit / ip_ban / captcha / business_403 / auth_wall 登录墙），决定是否升级访问策略；SiteAccessMemory。
  • captcha：CaptchaDetector + CaptchaSolver（NoOp 默认 + 可注入用户介入）。
  • ViewHost / ViewManager：内嵌浏览器容器抽象（WebContentsView / webview 两实现）。
  • browser-to-table：把网页表格/API 数据采集进 TabData（BrowserToTableDataset：字段类型推断 + 分页/行数限制 + 数据源类型 source_kind）。

Crawlspace —— 采集工作台 + 反检测

  • crawlspace-core：插件注册器（CrawlspaceRegistry）+ hooks/components/i18n/design-tokens，可扩展采集面板。
  • crawl-integration：HTTPEngine + WebContentsEngine 双引擎；RobotsChecker（robots.txt 合规）、PrivacyMasker（隐私脱敏）、CacheKeyGenerator、PayloadUtils。
  • anti-detect：AntiDetectManager —— UA 池（DynamicUAPoolManager / mobile-ua-generator / ChromeVersionTracker）、代理池 ProxyPool + ProxyHealthChecker、指纹（canvas/webgl/webrtc stealth）、会话持久化。
  • crawl-contracts：任务/反检测/提取/分页/网络层契约（AccessResult / Cookie / EngineType http|webcontents / SessionMode inherit|isolated|temporary）。
  • extraction-core：ExtractionEngine + selectors/transforms —— 结构化提取。media-core/media-capabilities：音视频/图片能力。
对天枢的启示：这三大应用是 TabTin「人与 Agent 操作同一份在线结果」的载体，天枢目前没有等价物（天枢只有本地工具 + 会话）。但注意：它们都共享同一套地基——权限（ResourcePermission / SessionShareResourceGrant）、版本（VersionHistory）、同步（增量 delta + outbox）、实时（collab-live + centrifugo）、存储（OSS + FileRecord）。天枢不必照抄这三个应用本身，而应优先把「地基」（权限 + 版本 + 增量同步 + 云存储）建好，再逐步长出自己的"天枢文档 / 天枢表格 / 天枢浏览器"。而且 TabTin 的浏览器能力（反检测/采集/登录墙）与天枢的"云端 Agent 协作"定位不完全匹配，应谨慎评估合规风险后选择性借鉴。

2天枢（dev）现状

2.1 技术栈与构成

构成

  • 数据：全部落 dataDir（getDataDir），单机单租户，天然「一机一份」。
  • 事件通道：transport/event-sinks.ts 全局 fan-out；SSE 每连接一个 sink，与 IPC 共用 ws/handlers.ts（传输中立——SSE 本身就是一条完整可用的远程通道，这对云同步/远程访问极其有利）。
  • 上行协议：POST /api/events（hello / strategy.set / chat-run / abort / approval.respond）；下行事件见 ALL_KNOWN_EVENTS（run.* / message.* / tool.* / approval.requested / ask_user / sub_agent.* / plan.* / goal.* …）。
  • 无认证：全库无登录逻辑；CORS 只放行 loopback；server 只绑 127.0.0.1 —— 这是本地安全边界，也是「云中继」方案的基础。

2.3 已有云端规划（mobile-cloud）——与本次需求高度相关

重要背景：天枢 dev/docs 里已有一份《mobile-cloud-architecture-plan.md》+《mobile-cloud-implementation-plan.md》（M0–M6），核心是 手机远程管理 + 统一登录：云服务器（阿里云 43.161.198.188 / www.tianshuapp.tech）只做中继，电脑 WSS 出站隧道，云不存业务数据，agent/会话/数据全在电脑本地。它已规划了：
  • 统一账号中心 /auth：注册/登录/refresh/me/JWKS，JWT（jose，access 30min/refresh 30d，refresh 哈希入库可撤销，scrypt 存密码）——未来所有服务共用。
  • /remote 远程服务：设备目录（register/devices/rename/unbind）+ WSS 隧道（心跳 25s/超时 70s/指数退避）+ 转发面（REST 透传 + SSE 桥接，透传 127.0.0.1:3456）。
  • 桌面 cloud-tunnel + 登录 UI；手机端 mobile-web + Capacitor → Android APK（复用 web/client stores/api/eventBus，M3 里程碑 MVP）；后续 iOS。
  • M4–M6：断连矩阵、错误码、加固、发布版 APK、本地通知、FCM 兜底。

也就是说：天枢的「登录/账号/云中继」地基已经设计好了，但方向是「远程操作自己的电脑」；本次用户要的「登录解锁 协作模式 / 共享模式 / 云储存（会话同步、多端同步、文件同步）」是在这个地基上往前再走一步——从「一人多端」走向「多用户协作」。

5天枢演进路线图（保留不登录 + 登录解锁）

5.1 核心原则与数据归属模型

三条铁律

  • R1 不登录完全可用：现在的一切（本地会话/角色/技能/模型/BYOK）保持零改动、零账号、零网络依赖。
  • R2 数据在本地，云只做能力扩展：账号、索引、同步副本、共享授权、桥接在中继侧；会话/文件原始数据默认留在本地，按用户授权才同步/共享。
  • R3 登录是"能力解锁器"而非"墙"：登录后解锁协作/共享/云存储/多端，而非登录才能用产品。

建议数据归属分层

数据本地（真源）云端（解锁后）
会话/消息sessions.db 保留增量同步副本（按会话授权）
文件/知识库dataDir 保留OSS 云盘副本（同步/共享用）
角色/技能/主题保留可选云备份 / 市场发布
账号/授权—统一账号中心（唯一）

5.2 分阶段实施

M0账号地基（复用已有 /auth 规划）
目标：统一账号中心跑通，为后续一切登录解锁能力做底座。
做法：按 mobile-cloud 规划的 /auth（register/login/refresh/me/JWKS，JWT + scrypt + refresh 可撤销）落地；桌面端登录 UI 与 token 安全存储（safeStorage）；不登录完全不触发。
M1会话云端同步（多端同步的第一步）
目标：登录用户在多台电脑/手机看到并接管同一批会话。
做法（关键设计决策）：
  • 方向：以「同步副本」而非「整体搬迁」切入——每台电脑仍以本地 sessions.db 为真源；登录后把选中的会话（或全部）增量同步到云（sessions/messages/runs 的 updated_at/version 增量拉取 + 合并）。
  • 同步协议复用现有 POST /api/events + SSE（传输中立、已在云中继验证）——把事件流「转发/落库」到云端即得实时同步，天枢 server 只加一个「同步 sink」。
  • 会话级 version + 简单 LWW（last-writer-wins）冲突合并，先用文档/表格数据校验；不上 CRDT（会话是 append 型，天然好合并）。
  • 离线自动重连 + 断点续传（对齐 collab 的 useOfflineReplay 思路，但实现简单得多）。
M2协作模式（借鉴 SessionShare 三档）
目标：登录用户能把会话授权给他人，可查看/可 fork，甚至可发言驱动。
做法：
  • 新建 SessionShare 等价模型（tianshu 版）：owner / grantee / can_view / can_fork / can_chat / status(pending|active|revoked) / access_epoch。
  • 查看：共享链接受权者只读拉取该会话（云端同步副本上读，不占用 owner 设备）。
  • fork：接收方把会话快照（正文+工具名+附件引用）抄写进自己的本地 sessions.db 成为独立会话——这是天枢本地优先模型下最自然的协作。
  • 对话（进阶，可后置）：can_chat 授权者经共享端点发言，驱动执行在 owner 电脑（复用云中继隧道，设备必须在线），费用/审批归 owner——完全对齐 TabTin shared-chat 语义。
  • 审计：SessionShareEvent 等价表（created/viewed/forked/chatted/revoked），「谁何时看过/fork」可追溯。
  • 实时：先做「共享会话的实时事件转发」（owner 电脑 → 云 → 授权者 SSE），不要求双向 CRDT。
M3共享模式（分享链接 + 组织内共享）
  • 链接分享：会话/知识库/文件生成 share_id 外链，可选密码（Django hasher 思路）、可选有效期；访客可只读查看（可再给 fork 权）。对齐 DocumentShare 的 shared/{share_id}/content + verify_password。
  • 组织内共享：登录用户可建「组织/工作空间」，成员之间一键共享（对齐 Organization + SpaceMembership）。
  • 权限模型：引入统一 ResourcePermission（viewer/editor/admin/owner）作为会话、文件、知识库的 ACL 执行面，共享只写授权记录——学习 TabTin「ACL 与共享来源分离、撤销只回收该来源权限」的设计（SessionShareResourceGrant），避免误伤。
M4云存储 / 文件同步
  • 文件云盘：复用 OSS presign→PUT→confirm 三步直传 + 秒传（hash）方案；天枢文件/知识库/媒体（devdata/media、知识库）按需同步为云端副本。
  • 多端文件同步：文件元数据（FileRecord 等价表）+ 内容哈希变更检测；按「同步策略」（全部/仅收藏/按会话）增量拉取。
  • 版本历史：给会话/文件加轻量 VersionHistory（快照 + 增量 diff，agent 编辑标 editor_type=agent，跨模块可追溯）——直接借鉴 TabTin 的通用版本表。
  • 配额：早期按账号给存储额度即可，不急着做钱包/计费。
M5实时与断连健壮性
  • 断连矩阵（电脑断网/休眠、手机弱网/切后台、服务器重启）自动恢复 + 状态一致（对齐 mobile-cloud M4）。
  • 共享会话实时事件重放（last-event-id）；同步副本的增量补齐（对齐 collab 离线回放但简化）。
  • 错误码规范化（device_offline / not_owner / token_expired / permission_denied）客户端分场景提示。
M6安全与治理（上线前必做）
  • 共享授权不绕过已有权限；403/404 防探测口径（对齐 isSharedAccessDenied）。
  • 撤销共享 → 实时订阅立即失效（access_epoch 机制）。
  • token 不落明文、日志不打印 token/密码、CORS 白名单、body 大小/并发/超时上限。
  • 审计流水完整可查（对齐 SessionShareEvent）。

6风险与关键决策

主要风险

风险说明应对
会话同步的合并语义多端同时编辑会话（尤其对话进行中）先 LWW + 按消息 append 合并；冲突在 UI 提示；不上 CRDT
「对话驱动」依赖 owner 设备在线TabTin 同款约束（执行在 owner 设备）can_chat 作为进阶档后置；先做查看 + fork
云上副本的安全会话含敏感上下文/工具输出默认不云存或端到端加密可选；共享按会话粒度显式授权 + 审计
本地 server 端口暴露一旦误暴露 3456 风险保持只绑 loopback；一切出网走云中继隧道（已验证方案）
范围蔓延协作/共享/存储/计费一起上会失控严格按 M0→M6 里程碑，每步有验收；初期不做计费/IM/CRDT
与已有 mobile-cloud 计划重叠/冲突两套云端方向需要统一把「远程操作」和「同步/协作/共享」统一为同一账号中心 + 同一数据平面，避免两套账号/存储
关键决策点（建议先拍板再动手）：
  1. 同步真源：会话真源留在本地、云做副本（推荐，符合天枢本地优先）——这决定云服务器不存业务原始数据，与既有 mobile-cloud「云只做中继」哲学一致。
  2. 协作档位：先做「查看 + fork」两档（低成本、离线友好），「发言驱动」第三档放后（需要设备在线语义）。
  3. 共享形态：先做「会话分享链接」，组织/工作空间后置（组织是另一套成员体系）。
  4. 云存储范围：先做「会话 + 文件 + 知识库」三类同步，媒体库（截图/录音/视频）量大，后置。
  5. 是否端到端加密：云副本若含敏感 Agent 上下文，建议会话级加密（本地密钥），成本可控且隐私叙事更好。
