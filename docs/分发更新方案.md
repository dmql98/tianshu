# tianshu 分发与更新方案(客户端安装后可持续更新)

> 目标:用户跑的是"我们打包好的 tianshu"(不要求用户装 Node),拿到后能**自动收到应用更新与内容更新**。
> 更新中心 = 你的 **store server**(与商业化方案 B 同源,把"发行中心"也握在自己手里)。

---

## 1. 背景:从 hermes 学到的"前后端分离更新"

hermes-studio 的设计关键,不是某个组件,而是一套"前端与后端解耦、可各自演进"的分发结构:

| hermes 机制 | tianshu 对应 | 作用 |
|:--- |:--- |:--- |
| client / server 独立包,独立产物 | `web/client` → `dist`静态、`web/server` → `dist` 可执行 | 更新时不相互牵连 |
| 生产环境 server 托管 client 静态 | server 加 koa-static 式托管 `../client/dist`(补上,当前 server **不托管**) | 前后端同源升级资源 |
| Vite dev 时 frontend/backend 双端口+代理 | tianshu dev 已是 3457/3456 | 开发热更与生产更新同理 |
| 发布 manifest(版本+下载+hash) | store server `/api/update` | 更新源稳定,只有你能发 |
| CLI `update`/桌面 updater | tianshu 内嵌"自更新检查 + 原子替换" | 用户无感知更新 |

结论:**tianshu 更新采用"前端增量 + 后端替换 + 内容独立升级"三段式**,均以你 store server 为权威源,签名为节点,sha256 校验。

## 1. 分发形态(打包给用户的产物)

用户最终拿到的是**免安装包**(免 Node):
```
tianshu-<version>-<os>-<arch>/
├──  node/                    # 捆绑的 Node 运行时(不依赖用户环境)
├──  server/
│    ├─ dist/                 # 编译后 server(= 现有 npm run build 产物)
│    └─ asset/                # tools/tool.json 等运行时资源(现有 build 保留)
├──  data/                    # DATA_DIR 默认"用户数据的根目录"(config.json 指向)
├──  start.bat / start.sh     # 一条命令启动,并打开浏览器
├──  tianshu-version.json      # 本机已安装版本 / 上次检查时间
└──  update-key.pub.json       # (P3) store server 公钥,更新验签配置
```
- 启动入口:`node <server>/dist/index.js --port <默认0>`,server 同时托管 `client/dist`,启动后 `start http://localhost`。
- 因此运行时要 server 托管 `client/dist`(改造当前 `index.ts`,新增 SPA fallback 与静态缓存头)。
- **分发包不包含任何付费内容**——商店内容通过方案 B 按授权下发。

## 2. 更新通道(store server)设计

在 store server 增加(也可复用商品目录):`GET /api/v1/update?channel=stable&platform=win64&from=0.8.0`

返回的 manifest:
```json
{
  "channel": "stable",
  "app": {
    "version": "0.8.2",
    "min": "0.7.0",            // 低于则必须强制升级
    "url": "https://cdn.yourstore/tianshu-0.8.2-win64.zip",
    "sha256": "...",
    "size": 52345678,
    "notes": "新增内置角色渲染性能、修复导出…",
    "force": false
  },
  "frontend": {                // 可选:仅前端增量
    "version": "0.8.2",        // 前端版本与 app 版本并列
    "hashManifest": "https://cdn.yourstore/frontend-0.8.2.json",
    "files": ["index-xxxx.js","assets/..."]   // md5 对齐的增量列表
  },
  "compat": { "contentApi": 2 } // 若内容 API 破坏性升级则提示
}
```

### 三段更新策略

1. **前端增量更新(高频,几乎每日)** — 因为 tianshu 前端是静态资源:
   - 用户启动/期间,server 检查 `GET /api/v1/update?frontendOnly=1`;
   - 以 manifest 里的 hash 为准,**只下载差异文件替换 `client/dist`**,无需重启 server;
   - 体积小、风险低,类比 hermes 里"只换 dist/client"。
2. **后端更新(低频,安全重启)** — 下载完整 server bundle,替换服务器文件,自热重启:
   - server 必须优雅关闭(现有 uncaught 处理已 for protection),更新后自动重新拉起;
   - `data/` 不动,会话/DB 保留。
3. **应用整体更新** — 前端+后端+配置文件,重打发布 zip,整包替换。

渠道:任何时刻支持 `stable / beta / dev` 三个 channel,store server 分下 channel 存储 manifests。

## 3. 客户端更新器(在地端实现)

新模块放在 **server 侧**,因为 client 仅浏览器:采用 `src/update/` 模块,在 server 进程内执行下载/校验/替换,进程重启即可生效:

```
src/update/
  manifest.ts     # 拉取/缓存/签名校验 update manifest
  downloader.ts   # 分段下载 + sha256 渐进校验 + 断点续下
  apply.ts        # 原子替换:下载到 temp → 校验 → 更名 → 备份→ 替换 → 重启指令
  notify.ts       # 推送 socket 事件给前端 UI("发现新版本/下载xx%/准备重启")
routes/update.ts  # /api/update 提供给浏览器 UI(前端调用后端检查)
```

### 更新流程(顺向)
```
start → server 启动 → 后台(可设闲时)调 check:
   GET store 的 update?from=<本版本>  → 
   ├若无更新 → 记录 checkedAt,无事发生
   ├若前端增量 → server 下载 diff zip → 校验 → 原子替换 client dist → 通知前端"请刷新"
   └若后端/全量:
      - 下载完整包到 `<data>/update/.tmp`
      - 校验 sha256 + 签名 → 停旧 server(旧 pid 退出)
      - 替换 (保留 `data/` 与 `dist/` 之外) → 重启新 server
      - 新 server 自检 `/health` 通过后完成,失败回滚旧目录
```

### 失败与安全
- **原子替换**:新目录 `app-0.8.2/` 到位后,切换 `current` 符号连接/rename,旧目录保留 1 份回滚点。
- **完整性**:服务器公钥验签 + sha256 双重;下载失败(网络/中断) → 删除 temp,下次续。
- **强制升级**:`force:true` 或当前版本 `< min`,启动直接弹窗"需要更新",不更新不能继续(保证付费内容兼容等)。

## 5. 安全模型(更新通道)

- **签名**:store server 对每个 manifest 与 zip 用 **Ed25519(服务端私钥)** 签名;tianshu 里预置**服务器公钥**,验证后方可执行。私钥只在你的服务器。
- **降级防护**:manifest 里 `version` 经签名,客户端拒绝降级。
- **供应链**:不要把第三方依赖直接进离线运行时,打包时锁定 `package.json` 与 lockfile(一键 `npm ci`)。

---

## 6. 内容(角色/皮肤)更新与 App 更新的关系

| 更新类型 | 通道 | 频率 | 操作 | 需重启 |
| --- | --- | --- | --- | --- |
| 内容角色包/皮肤 | store server `/api/v1/download/package`(**方案 B**) | 按上架 | 授权下发替换 | 否(仅字符级) |
| 前端增量 | `/api/v1/update?frontendOnly` | 频繁 | dist 替换 | 否(刷新即可) |
| 后端升级 | 同上 `app` | 低频 | server 替换 | 是(自动,可暂停) |
| 全量不兼容 | 同上 `force` | 罕见 | 整体替换 | 是强制 |

两套系统并行:内容靠授权、App 靠版本,互不阻塞。

## 7. 里程碑(可用性排序)

### P0: server 托管前端 + 发布管线
- [ ] 改造 `web/server/src/index.ts`:新增静态中间件 SPA fallback 托管 `web/client/dist`(注意已有 `/api`、`/socket.io` 排除与 Cache-Control)。
- [ ] 新增 `scripts/package.mjs`:build server + client → 打包 `tianshu-<v>-win64.zip`(含 runtime 目录结构)。
- [ ] `start.bat` 一键启动并打开浏览器。

### P1: 更新检查与通知
- [ ] store server `/api/v1/update` 返回 manifest(静态 JSON 文件即可起步)。
- [ ] tianshu 端 `src/update/*`,`GET 检查`;前端右上角设置页"检查更新"按钮 + socket 通知。
- [ ] 前端增量替换(dist)实现,P2 前最常用。

### P2: 后端/全量自助更新(自动重启+回滚)
- [ ] 完整 zip 下载/校验/原子替换 + health 自检 + 回滚点。
- [ ] 强制升级与 channel 切换(settings.json)。

### P3: 发布 CI 与运维
- [ ] GitHub Actions(或 git tag CI)构建三平台/包,上传 store server bucket + 写 manifest。
- [ ] 更新通知站/公告。

## 8. 与商业化方案 B 的合并

- store server 同时掌握"授权 + 包体 + 更新"三件事,一个可信源,一个管理后台。
- 用户主流程:
  1. 从你的发布面获得连通包(不含内容)
  2. 首启动 → server 托 UI → 注册设备(商店 B)→ 目录 → 兑换码 / 购买
  3. 每次启动 → 更新检查(前端增量/后端升级)+ 授权续期
- 商业与更新在**自己的服务器**闭环,避免依赖任何第三方发行面(GitHub/App Store/云厂商),可控性强。
